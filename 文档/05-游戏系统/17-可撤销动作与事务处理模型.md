# 17. 可撤销动作与事务处理模型

## 1. 引言

本文档旨在详细阐述《影之诗：超越》核心游戏逻辑中，关于**可撤销的玩家动作**（Cancellable Player Actions）的架构设计与实现流程。随着游戏机制的复杂化，特别是引入需要玩家在动作执行过程中进行目标选择的能力（如“入场曲：选择一个单位...”），我们需要一个健壮的系统来处理动作的“暂停”、“恢复”与“取消”，同时保证游戏结算的严格顺序和原子性。

本文档是我们进行相关功能重构和开发的**权威指南**。

## 2. 核心概念定义

为了构建此系统，我们首先定义以下核心概念：

### 2.1. 玩家主要动作 (`IPlayerActionEvent`)

并非所有游戏事件都代表玩家的直接意图。我们将那些由玩家直接发起的、构成其决策核心的动作所产生的事件，定义为**玩家主要动作事件**。

*   **识别方式**：通过实现一个空的标记接口 `IPlayerActionEvent` 来识别。
*   **示例**：`PlayCardEvent`, `AttackEvent`, `EvolveEvent` 都是典型的玩家主要动作事件。而 `SummonEvent`, `DamageEvent` 等则是这些主要动作引发的连锁反应或事实结果，不属于主要动作。

### 2.2. 主要能力 vs. 连锁能力

根据动作是否可撤销，我们将由事件触发的能力分为两类：

*   **主要能力 (Primary Ability)**：与玩家主要动作**直接绑定**的能力，是动作本身不可分割的一部分。这类能力的目标选择过程是**可撤销**的。
    *   **识别条件**：
        1.  其触发器监听一个实现了 `IPlayerActionEvent` 的事件。
        2.  能力的来源卡牌（`SourceCard`）与触发事件的来源卡牌是同一个。
    *   **示例**：卡牌A的“入场曲”（监听 `PlayCardEvent`）。

*   **连锁能力 (Chained Ability)**：响应游戏状态变化而触发的能力，是既成事实的后果。这类能力一旦触发，其流程是**不可撤销**的。
    *   **识别条件**：所有不满足“主要能力”条件的触发式能力。
    *   **示例**：卡牌B的“当有其他单位进场时...”能力（监听 `SummonEvent`）；卡牌C的“当任意玩家使用卡牌时...”能力（监听 `PlayCardEvent`，但 `SourceCard` 与事件来源不同）。

### 2.3. 触发时机 (`TriggerTiming`)

为了精确控制能力在事件生命周期中的执行顺序，`TriggerConfig` 中定义了 `TriggerTiming` 枚举：

*   `Before`：在事件提交（`Commit`）**之前**执行。通常用于替代性效果或防御性效果（如“使即将受到的伤害变为0”）。
*   `On`：在事件提交（`Commit`）**之前**，但在 `Before` 能力之后执行。这是绝大多数能力的默认时机。
*   `After`：在事件提交（`Commit`）**之后**，即游戏状态已经发生改变后执行。通常用于响应“既成事实”的效果（如“一个单位被破坏后，抽一张牌”）。

### 2.4. 可提交事件 (`ICommittableEvent`)

这是实现“延迟状态变更”的核心机制。

*   **职责分离**：`EffectHandler` 的职责不再是直接修改游戏状态，而是生成一个或多个实现了 `ICommittableEvent` 接口的事件。
*   **延迟执行**：这些事件是状态变更的“计划书”。只有当它们的 `Commit()` 方法被调用时，其中封装的状态变更逻辑（如 `playerState.ExecutePlayCard()`）才会真正执行。
*   **预知未来**：这使得我们可以在 `Commit()` 之前，就能拿到所有待处理的事件，并预先分析它们将会触发哪些能力，从而实现复杂流程的编排。

### 2.5. 目标解析生命周期 (`Target.NeedsResolution`)

为了解决在复杂流程中对同一个能力进行多次目标解析的问题，我们采用让 `Target` 对象自身管理其解析状态的机制，取代了繁琐的 `partialResult` 传递。

*   **状态管理**：每个运行时的 `Target` 对象内部维护一个布尔值 `NeedsResolution`（默认为 `true`）和一个列表 `ResolvedTargets`。
*   **幂等解析**：当调用一个能力的目标解析方法时，它会检查其下的每个 `Target`。只有当 `target.NeedsResolution` 为 `true` 时，才会执行实际的解析逻辑。
*   **状态变更**：一旦解析完成，结果会存入 `target.ResolvedTargets`，同时 `NeedsResolution` 被设为 `false`。
*   **结果复用**：后续任何对该 `Target` 的重复解析请求，都会因为 `NeedsResolution` 为 `false` 而被自动跳过，并直接使用已有的 `ResolvedTargets` 结果。
*   **外部写入**：当玩家做出选择后，外部服务可以通过 `target.SetResolvedTargets()` 方法将最终结果写回，并同步更新 `NeedsResolution` 状态。

### 2.6. 事件处理队列

为了实现精确的事件处理顺序，系统维护两个核心队列：

*   **事件暂存区 (`EventStagingArea`)**: 一个临时的、高优先级的队列 (`Queue<IGameEvent>`)，用于处理需要**立即递归解决**的事件链。主要来源是 `Before` 阶段和 `Commit` 阶段产生的子事件。
*   **效果队列 (`EffectQueue`)**: 一个全局的、较低优先级的队列 (`Queue<Effect>`)，用于存放那些需要**延迟执行**的效果。主要来源是 `On` 和 `After` 阶段触发的能力。

## 3. `GameActionTransactionService` 详解

为了将复杂的事务流程与 `GameService` 的核心职责解耦，我们引入 `GameActionTransactionService`。

### 3.1. 核心职责

该服务的**单一职责**是：**编排一个玩家动作从请求到最终结算的、具有事务性的完整生命周期**。它管理事件的触发、提交和连锁反应，确保游戏逻辑的正确性和原子性。

### 3.2. 核心处理流程

系统围绕“事件暂存区”和“效果队列”进行循环处理，直至两者都为空。**暂存区的优先级始终高于效果队列**。

```mermaid
graph TD
    A[Start Transaction with Initial Events] --> B[Add Initial Events to EventStagingArea];
    B --> C{Loop while EventStagingArea or EffectQueue is not empty};
    C -- Yes --> D{Is EventStagingArea not empty?};
    D -- Yes --> E[Dequeue Event 'E' from StagingArea];
    E --> F[ProcessEvent(E)];
    F --> C;
    D -- No --> G[Dequeue Effect 'Eff' from EffectQueue];
    G --> H[Execute 'Eff' to get Sub-Events];
    H --> I[Add Sub-Events to EventStagingArea];
    I --> C;
    C -- No --> J[End Transaction];

    subgraph ProcessEvent(E)
        direction TB
        P1[Start] --> P2[Process 'Before' Abilities];
        P2 --> P3[Execute 'Before' Effects & Get Sub-Events];
        P3 --> P4[For each Sub-Event, RECURSIVELY call ProcessEvent];
        P4 --> P5[Process 'On' Abilities];
        P5 --> P6[Enqueue 'On' Effects into EffectQueue];
        P6 --> P7[Commit Event 'E' & Get Sub-Events];
        P7 --> P8[For each Sub-Event, RECURSIVELY call ProcessEvent];
        P8 --> P9[Process 'After' Abilities];
        P9 --> P10[Enqueue 'After' Effects into EffectQueue];
        P10 --> P11[End];
    end

```

**流程详解:**

1.  **启动**: 玩家动作产生的一批初始事件被加入“事件暂存区”。
2.  **主循环**:
    *   只要“事件暂存区”或“效果队列”不为空，循环就继续。
    *   **优先处理暂存区**: 如果暂存区有事件，取出一个进行处理。
    *   **处理效果队列**: 只有当暂存区清空后，才从效果队列中取出一个效果来执行。执行效果产生的新事件会再次进入暂存区。
3.  **`ProcessEvent` (递归核心)**: 这是处理单个事件的生命周期函数。
    *   **`Before` 阶段 (立即递归)**: 触发 `Before` 能力，立即执行其产生的 `Effect`，并将 `Effect` 产生的子事件**立即进行递归处理**。这确保了所有前置、替代性效果都在事件本身提交前完成结算。
    *   **`On` 阶段 (排队)**: 触发 `On` 能力，但其产生的 `Effect` **不立即执行**，而是被加入到全局的“效果队列”中，等待后续处理。
    *   **`Commit` 阶段 (立即递归)**: 调用事件的 `Commit()` 方法，使其真正改变游戏状态。`Commit` 产生的子事件被视为高优先级，**立即进行递归处理**。
    *   **`After` 阶段 (排队)**: 触发 `After` 能力，其产生的 `Effect` 同样被加入“效果队列”中。
    *   **条件与目标解析**：能力的 `CheckConditions` 与 `ResolveTargets` 在“生成 Effect”时执行，并使用带 `SourceCard/TriggeringEvent` 的能力上下文；触发筛选阶段只负责匹配时点与排序，避免重复评估导致 `On`/`After` 语义混淆。
4.  **结束**: 当两个队列都为空时，整个事务处理结束。

## 4. EffectHandler 到 ICommittableEvent 的重构模式

随着 `GameActionTransactionService` 的引入，我们需要一套标准的作业程序（SOP）来将旧的、直接修改状态的 `EffectHandler` 重构为符合新事务处理模型的、基于事件的模式。

### 4.1. 核心思想：带生命周期的 `ICommittableEvent`

我们系统的核心是一个**带生命周期的 `ICommittableEvent` 混合模型**。这个模型兼顾了职责分离的清晰性和处理复杂事前触发逻辑（`Before`/`On`）的兼容性。`ICommittableEvent` 自身就是一个生命周期状态机，它从一个“意图”开始，经过验证和触发 `Before`/`On` 能力后，最终通过 `Commit` 成为“事实”。

### 4.2. 组件职责划分

1.  **`EffectHandler`：守门员与调度员**
    *   **职责一：守门 (Gatekeeping)**。`Handler` 是效果的入口，负责**所有前置合法性检查**。只有当所有条件都满足时，它才会创建事件。这确保了所有后续生成的事件都是**绝对合法、确切可执行的**。
    *   **职责二：调度 (Dispatching)**。对于可能作用于多个目标的效果，`Handler` 必须调用 `_targetProcessingService.ProcessTargets`。这个服务会遍历所有目标，并为**每一个目标**执行一个指定的动作。

2.  **`ProcessTargets` 内的委托：指令的创建工厂**
    *   **职责：创建指令 (Command Creation)**。这个传递给 `ProcessTargets` 的委托，其唯一职责就是为**单个目标**创建一个对应的 `ICommittableEvent` 指令。

3.  **`ICommittableEvent` (指令事件)：逻辑的封装体**
    *   **职责：封装执行逻辑 (Encapsulating Execution Logic)**。事件的 `Commit` 方法封装了当该指令被执行时，需要发生的**所有后续逻辑**。它负责调用实体方法，将宏观意图分解为微观事实。

4.  **实体方法 (如 `CardInstance.PerformAttack`)：子事件的生成器**
    *   **职责：分解为原子事件 (Decomposition to Atomic Events)**。实体方法**不再直接修改状态**。它的职责是把一个宏观动作（如“攻击”）分解成一系列最微观、最原子化的**事实事件**（如 `ClashEvent`, `DamageEvent`），并将它们作为结果返回。

5.  **`GameActionTransactionService`：最终的驱动引擎**
    *   **职责：驱动执行 (Driving Execution)**。事务服务是整个流程的引擎。它负责根据第3节描述的双队列模型，编排 `ICommittableEvent` 的完整生命周期。

### 4.3. 标准重构流程 (SOP)

以 `AttackEffectHandler` 的重构为例：

1.  **分析与检查实体方法**：
    *   分析 `AttackEffectHandler`，确认其核心是调用 `CardInstance.PerformAttack`。
    *   检查 `PerformAttack` 方法。在重构前，它直接修改状态。

2.  **重构实体方法**：
    *   修改 `PerformAttack` 方法，移除所有直接的状态变更代码（如 `AttacksThisTurn++`, `TakeDamage`）。
    *   使其只负责计算战斗后果，并创建对应的原子事件（`ClashEvent`, `DamageEvent`），最后将这些事件包装在 `DomainOperationResult` 中返回。

3.  **创建/迁移 `ICommittableEvent`**：
    *   将 `AttackEvent` 从 `CoreGameEvents.cs` 迁移到独立的 `AttackEvent.cs` 文件中。
    *   使其实现 `ICommittableEvent` 接口。
    *   实现 `Commit` 方法。该方法内部调用重构后的 `attacker.PerformAttack(target)`，并返回结果。

4.  **重构 `EffectHandler`**：
    *   修改 `AttackEffectHandler.Apply` 方法。
    *   **保留**前置检查逻辑（调用 `attacker.CanPerformAttack`）。
    *   **保留**对 `_targetProcessingService.ProcessTargets` 的调用。
    *   修改传递给 `ProcessTargets` 的委托，使其**只负责创建** `new AttackEvent(attacker, target)` 并将其放入 `DomainOperationResult` 中返回。

遵循以上步骤，即可将任何旧的 `EffectHandler` 安全、可靠地重构到新的事务处理模型中。
