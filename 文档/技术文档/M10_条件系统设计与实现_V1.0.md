# M10: 条件系统设计与实现 V1.0

## 1. 概述

本文档详细描述卡牌能力系统中 **触发条件 (Trigger Conditions)** 的设计理念、技术选型、语法定义、实现细节以及与系统其他部分的交互。

本模块的目标是提供一个足够灵活、强大且高性能的机制，用于判断卡牌能力在特定游戏事件发生时是否应该被触发。

## 2. 技术选型决策 (2025-06-03)

经过对多种方案（包括字符串表达式解析、JSON 配置、嵌入式脚本引擎等）的分析和讨论，最终确定采用以下技术方案：

*   **核心架构:** **抽象语法树 (AST) + C# 表达式树编译 (`System.Linq.Expressions`)**
    *   **理由:** 该方案提供了最佳的性能（接近原生 C# 代码）、强类型检查以及处理复杂逻辑的能力。编译后的委托可以高效执行，并且易于缓存。
*   **解析器实现:** **优先考虑使用 [Sprache](https://github.com/sprache/Sprache) 库**
    *   **理由:** Sprache 是一个基于 Parser Combinator 的纯 C# 库，与 C# 集成紧密，学习曲线相对平缓，无需外部工具或代码生成步骤，适合快速迭代和构建中等复杂度的解析器。如果后续语法复杂度极高，再评估切换到 ANTLR 的可能性。
*   **配置来源与处理:**
    *   **主要方式:** 支持处理存储在数据库中的 **条件字符串 DSL**。使用 Sprache 解析 DSL 字符串，构建 AST，然后转换为 C# 表达式树并编译。
    *   **前端集成:** 支持处理由前端 UI 构建器生成的 **JSON 配置**。后端将提供逻辑，直接将反序列化后的 JSON 对象（映射到 `Condition` 类层次结构）转换为 C# 表达式树并编译。
    *   **混合支持:** 系统将同时具备处理字符串 DSL 和 JSON 配置的能力，为不同来源的条件定义提供统一的运行时执行机制。
*   **运行时:**
    *   编译后的 `Func<ConditionContext, bool>` 委托将被缓存，以避免重复编译开销。
    *   条件评估时，根据当前的 `ConditionContext` 执行对应的缓存委托。

## 3. 条件表达式 DSL 语法设计

### 3.1 设计原则 (V0.3)

*   **可读性优先:** 语法应尽可能接近自然语言或常见的编程表达式。
*   **标准化:** 遵循标准的算术和逻辑运算符及其优先级（如 `+`, `-`, `*`, `/`, `%`, `==`, `!=`, `>`, `<`, `>=`, `<=`, `&&`, `||`, `!`, `()`）。避免使用非标准符号或自定义优先级规则。
*   **关注点分离:** DSL 主要负责 **条件评估** 逻辑。复杂的 **目标筛选** 逻辑应由专门的目标选择器 (Target Selector) 处理，DSL 只需判断是否存在满足条件的潜在目标。
*   **类型安全:** 虽然 DSL 本身是字符串，但其最终会被编译为强类型的 C# 表达式树，在编译阶段进行类型检查。
*   **可扩展性:** 易于添加新的函数、属性和上下文访问点。

### 3.2 核心语法元素

1.  **字面量 (Literals):**
    *   整数: `10`, `-5`
    *   布尔值: `true`, `false`
    *   字符串: `"some text"` (主要用于比较，如卡牌名称、特性等)
    *   枚举值: `EnumType.EnumValue` (例如 `CardType.Follower`, `TriggerTiming.Play`)

2.  **上下文访问 (Context Access):** 使用点 `.` 操作符访问 `ConditionContext` 中的属性及其嵌套属性。
    *   `Source`: 访问触发能力的卡牌实例 (`ConditionContext.SourceCard`)。
        *   示例: `Source.Attack >= 5`, `Source.CardType == CardType.Follower`, `Source.Owner.PP`
    *   `Self`: 访问能力来源卡牌的拥有者玩家状态 (`ConditionContext.SelfPlayer`)。
        *   示例: `Self.PP >= Source.Cost`, `Self.Hand.Count > 0`
    *   `Enemy`: 访问对手玩家状态 (`ConditionContext.EnemyPlayer`)。
        *   示例: `Enemy.Leader.HP <= 10`, `Enemy.Field.Count == 5`
    *   `Event`: 访问触发条件评估的游戏事件 (`ConditionContext.TriggeringEvent`)。需要根据具体事件类型访问其属性。
        *   示例: `Event.Type == EventType.DamageDealt && (Event as DamageEvent).Amount >= 3`, `(Event as CardPlayedEvent).PlayedCard.Cost <= Self.PP` (注意类型转换的表达方式，实际实现时可能提供更简洁的语法糖或辅助函数)
    *   `Vars`: 访问能力内部变量 (`ConditionContext.AbilityVariables`)。
        *   示例: `Vars.Counter < 3`, `Vars.IsEnabled == true`
    *   `State`: 访问全局游戏状态 (`ConditionContext.CurrentGameState`)，用于访问那些不直接归属于 `Self` 或 `Enemy` 的状态信息，或进行更复杂的查询（通常通过内置函数）。
        *   示例: `State.TurnNumber > 5`

3.  **运算符 (Operators):**
    *   算术: `+`, `-`, `*`, `/`, `%`
    *   比较: `==`, `!=`, `>`, `<`, `>=`, `<=`
    *   逻辑: `&&` (AND), `||` (OR), `!` (NOT)
    *   括号: `()` 用于控制运算优先级。

4.  **内置函数 (Built-in Functions):** 用于执行更复杂的操作，特别是涉及集合查询。
    *   **`Exists(collection_expr, item_condition_expr)`:** 判断 `collection_expr` 返回的集合中是否存在至少一个元素满足 `item_condition_expr`。
        *   `collection_expr`: 一个返回集合的表达式 (例如 `Self.Field`, `Enemy.Hand`, `State.AllUnits`)。
        *   `item_condition_expr`: 一个字符串形式的嵌套条件表达式，用于评估集合中的每个元素。在该表达式内部，可以使用预定义的标识符（如 `item` 或 `card`）来引用当前正在检查的元素。
        *   示例: `Exists(Self.Field, "item.Attack > 5 && item.HasTrait(\"Officer\")")` (检查己方场上是否存在攻击力大于5且具有“指挥官”词条的随从)
        *   示例: `Exists(Enemy.Hand, "card.Cost <= 2")` (检查对方手牌中是否存在费用小于等于2的卡牌)
    *   **`Count(collection_expr, item_condition_expr)`:** 返回 `collection_expr` 集合中满足 `item_condition_expr` 的元素数量。
        *   示例: `Count(Self.Field, "item.HP <= 2") >= 3` (检查己方场上生命值小于等于2的随从数量是否至少为3)
    *   **`All(collection_expr, item_condition_expr)`:** 判断 `collection_expr` 集合中的**所有**元素是否都满足 `item_condition_expr`。如果集合为空，通常返回 `true`。
        *   示例: `All(Enemy.Field, "item.CanAttack == false")` (检查对方场上所有随从是否都不能攻击)
    *   **`HasTrait(target_expr, trait_name)`:** 判断 `target_expr` 返回的目标是否拥有指定的特性 (Trait)。
        *   示例: `HasTrait(Source, "Commander")`, `HasTrait(Event.Target, "Ward")`
    *   **其他可能的函数:** `Max(collection_expr, value_expr)`, `Min(...)`, `Sum(...)`, `RandomInt(min, max)`, `GetVariable(name)`, `GetGlobalCounter(name)` 等，根据需要添加。

## 4. ConditionContext 定义

`ConditionContext` 是在运行时传递给已编译条件委托（`Func<ConditionContext, bool>`）的上下文信息包。它的设计目标是提供评估**前置条件**（如卡牌能否打出、能力是否满足触发门槛）所需的核心信息。

**重要区分:**

*   **前置条件 (Activation/Trigger Condition):** 在动作宣告或事件触发时评估，发生在目标选择之前。此时关心的是游戏状态和**是否存在潜在的合法目标**。使用 `ConditionContext`。
*   **效果条件 (Effect Condition):** 在效果结算过程中评估，发生在目标选择之后。此时关心的是**已选定的目标**和游戏状态。将使用一个更具体的上下文（例如 `EffectExecutionContext`，包含 `ConditionContext` 和 `SelectedTargets`），但这部分将在效果系统设计中详述。

**`ConditionContext` 结构:**

```csharp
/// <summary>
/// 为条件评估提供运行时上下文信息。主要用于前置条件判断。
/// </summary>
public class ConditionContext
{
    /// <summary>
    /// 触发本次条件评估的游戏事件实例。
    /// </summary>
    public IGameEvent TriggeringEvent { get; }

    /// <summary>
    /// 触发此能力检查的卡牌实例。
    /// </summary>
    public CardInstance SourceCard { get; }

    /// <summary>
    /// 当前的游戏状态快照。提供对玩家、场地、手牌等的访问。
    /// **注意:** GameState 需要提供丰富的查询方法 (如 GetPlayer, GetOpponent,
    /// GetFieldUnits, FindPotentialTargets(filter), CountUnitsMatching(filter) 等)
    /// 以支持对潜在目标的判断。
    /// </summary>
    public GameState CurrentGameState { get; }

    /// <summary>
    /// 能力自身的内部变量（例如计数器、状态标记等，如果存在）。
    /// </summary>
    public AbilityVariables? AbilityVariables { get; } // 可能为 null

    // 构造函数
    public ConditionContext(IGameEvent triggeringEvent, CardInstance sourceCard, GameState currentGameState, AbilityVariables? abilityVariables)
    {
        TriggeringEvent = triggeringEvent;
        SourceCard = sourceCard;
        CurrentGameState = currentGameState;
        AbilityVariables = abilityVariables;
    }

    // --- 便捷访问属性 (示例，根据 DSL 设计决定具体实现) ---

    /// <summary>
    /// 获取能力来源卡牌的拥有者玩家状态。
    /// </summary>
    public PlayerState SelfPlayer => CurrentGameState.GetPlayer(SourceCard.OwnerPlayerId);

    /// <summary>
    /// 获取对手玩家状态。
    /// </summary>
    public PlayerState EnemyPlayer => CurrentGameState.GetOpponent(SourceCard.OwnerPlayerId);

    // 可以根据需要添加更多便捷属性，例如直接访问事件的特定属性
    // public int DamageAmount => (TriggeringEvent as DamageEvent)?.Amount ?? 0;
}
```

## 5. AST 节点定义

抽象语法树 (AST) 是 DSL 字符串经过解析器处理后生成的树状数据结构。它以代码友好的方式表示了原始表达式的结构和语义，是后续转换为 C# 表达式树的中间表示。

### 5.1 基础节点接口

所有 AST 节点都实现一个基础接口或继承自一个基类，以便统一处理。

```csharp
/// <summary>
/// AST 节点的基础接口。
/// </summary>
public interface IAstNode { }

/// <summary>
/// 表示一个可以计算出值的表达式节点。
/// </summary>
public interface IExpressionNode : IAstNode { }
```

### 5.2 字面量节点 (Literal Nodes)

表示 DSL 中的常量值。

```csharp
public class IntegerLiteralNode : IExpressionNode
{
    public int Value { get; }
    public IntegerLiteralNode(int value) { Value = value; }
}

public class BooleanLiteralNode : IExpressionNode
{
    public bool Value { get; }
    public BooleanLiteralNode(bool value) { Value = value; }
}

public class StringLiteralNode : IExpressionNode
{
    public string Value { get; }
    public StringLiteralNode(string value) { Value = value; }
}

public class EnumLiteralNode : IExpressionNode
{
    public Type EnumType { get; }
    public string EnumValueName { get; } // 存储枚举值的名称字符串
    public EnumLiteralNode(Type enumType, string enumValueName)
    {
        EnumType = enumType;
        EnumValueName = enumValueName;
    }
    // 在转换为表达式树时，会使用 Enum.Parse 或类似方法获取实际枚举值
}
```

### 5.3 上下文访问节点 (Context Access Node)

表示对 `ConditionContext` 及其属性的访问。

```csharp
public class ContextAccessNode : IExpressionNode
{
    /// <summary>
    /// 访问路径，例如 ["Self", "PP"] 或 ["Event", "DamageEvent", "Amount"]
    /// </summary>
    public List<string> PathSegments { get; }

    public ContextAccessNode(List<string> pathSegments)
    {
        PathSegments = pathSegments;
    }
}
```
*注意：对于事件属性的访问，可能需要包含类型转换信息，例如 `(Event as DamageEvent).Amount` 可以表示为 `PathSegments = ["Event", "as DamageEvent", "Amount"]` 或通过专门的类型转换节点处理。这里简化为字符串列表，具体实现由解析器和转换器决定。*

### 5.4 运算符节点 (Operator Nodes)

表示一元和二元运算。

```csharp
public enum BinaryOperatorType
{
    Add, Subtract, Multiply, Divide, Modulo, // 算术
    Equal, NotEqual, GreaterThan, LessThan, GreaterThanOrEqual, LessThanOrEqual, // 比较
    And, Or // 逻辑
}

public class BinaryOperatorNode : IExpressionNode
{
    public BinaryOperatorType OperatorType { get; }
    public IExpressionNode Left { get; }
    public IExpressionNode Right { get; }

    public BinaryOperatorNode(BinaryOperatorType operatorType, IExpressionNode left, IExpressionNode right)
    {
        OperatorType = operatorType;
        Left = left;
        Right = right;
    }
}

public enum UnaryOperatorType
{
    Not, // 逻辑非
    Negate // 算术负 (如果支持)
}

public class UnaryOperatorNode : IExpressionNode
{
    public UnaryOperatorType OperatorType { get; }
    public IExpressionNode Operand { get; }

    public UnaryOperatorNode(UnaryOperatorType operatorType, IExpressionNode operand)
    {
        OperatorType = operatorType;
        Operand = operand;
    }
}
```

### 5.5 函数调用节点 (Function Call Node)

表示对内置函数的调用。

```csharp
public class FunctionCallNode : IExpressionNode
{
    public string FunctionName { get; }
    public List<IExpressionNode> Arguments { get; }

    public FunctionCallNode(string functionName, List<IExpressionNode> arguments)
    {
        FunctionName = functionName;
        Arguments = arguments;
    }
}
```
*对于 `Exists`, `Count`, `All` 等函数，其第二个参数（`item_condition_expr`）在 DSL 中是字符串。在 AST 中，可以将其表示为一个 `StringLiteralNode`，在转换为表达式树时，需要递归调用解析器和编译器来处理这个嵌套的条件字符串。*

### 5.6 示例 AST

DSL 表达式: `Self.PP >= Source.Cost && Exists(Self.Field, "item.Attack > 5")`

对应的 AST (简化表示):

```
BinaryOperatorNode (OperatorType: And)
|
+-- Left: BinaryOperatorNode (OperatorType: GreaterThanOrEqual)
|   |
|   +-- Left: ContextAccessNode (PathSegments: ["Self", "PP"])
|   |
|   +-- Right: ContextAccessNode (PathSegments: ["Source", "Cost"])
|
+-- Right: FunctionCallNode (FunctionName: "Exists")
    |
    +-- Arguments[0]: ContextAccessNode (PathSegments: ["Self", "Field"])
    |
    +-- Arguments[1]: StringLiteralNode (Value: "item.Attack > 5")
```

这个 AST 结构清晰地表达了原始 DSL 的计算逻辑，为下一步生成 C# 表达式树奠定了基础。

## 6. JSON 配置结构

除了 DSL 字符串，条件也可以通过 JSON 结构来定义。这对于可视化编辑器生成条件或在不支持 DSL 解析的环境中使用非常有用。JSON 结构的设计直接映射自 AST 节点。

### 6.1 基础结构与节点类型

每个 JSON 条件对象都有一个 `type` 字段，用于标识其对应的 AST 节点类型。

```json
{
  "type": "NodeType",
  // ... 其他属性 ...
}
```

支持的 `NodeType` 包括：

*   `IntegerLiteral`: 整数常量
*   `BooleanLiteral`: 布尔常量
*   `StringLiteral`: 字符串常量
*   `EnumLiteral`: 枚举常量
*   `ContextAccess`: 访问上下文属性
*   `BinaryOp`: 二元运算
*   `UnaryOp`: 一元运算
*   `FunctionCall`: 内置函数调用

### 6.2 具体节点结构

1.  **字面量 (Literals):**
    *   整数: `{ "type": "IntegerLiteral", "value": 10 }`
    *   布尔值: `{ "type": "BooleanLiteral", "value": true }`
    *   字符串: `{ "type": "StringLiteral", "value": "Commander" }`
    *   枚举值: `{ "type": "EnumLiteral", "enumType": "CardType", "value": "Follower" }`
        *   `enumType`: 枚举类型的名称 (字符串)。
        *   `value`: 枚举值的名称 (字符串)。

2.  **上下文访问 (Context Access):**
    *   `{ "type": "ContextAccess", "path": ["Self", "PP"] }`
    *   `{ "type": "ContextAccess", "path": ["Event", "as DamageEvent", "Amount"] }`
        *   `path`: 一个字符串数组，表示访问路径。类型转换可以通过特定格式的字符串（如 `"as TypeName"`) 嵌入路径中，具体解析逻辑由后端实现。

3.  **二元运算符 (Binary Operator):**
    *   `{ "type": "BinaryOp", "operator": "GreaterThanOrEqual", "left": { ... }, "right": { ... } }`
        *   `operator`: 运算符类型名称 (字符串，对应 `BinaryOperatorType` 枚举，例如 `Add`, `Subtract`, `Equal`, `NotEqual`, `And`, `Or` 等)。
        *   `left`, `right`: 嵌套的 JSON 条件对象。

4.  **一元运算符 (Unary Operator):**
    *   `{ "type": "UnaryOp", "operator": "Not", "operand": { ... } }`
        *   `operator`: 运算符类型名称 (字符串，对应 `UnaryOperatorType` 枚举，例如 `Not`, `Negate`)。
        *   `operand`: 嵌套的 JSON 条件对象。

5.  **函数调用 (Function Call):**
    *   `{ "type": "FunctionCall", "functionName": "HasTrait", "arguments": [ { "type": "ContextAccess", "path": ["Source"] }, { "type": "StringLiteral", "value": "Commander" } ] }`
    *   `{ "type": "FunctionCall", "functionName": "Exists", "arguments": [ { "type": "ContextAccess", "path": ["Self", "Field"] }, { /* 嵌套的 item 条件 JSON 对象 */ } ] }`
        *   `functionName`: 函数名称 (字符串)。
        *   `arguments`: 一个 JSON 条件对象的数组。对于 `Exists`, `Count`, `All` 等函数的第二个参数（条件表达式），它本身也是一个完整的 JSON 条件对象。在处理这个嵌套条件时，需要注意其内部上下文（例如，如何引用集合中的 `item`）。这通常在后端转换为表达式树时处理，例如通过构造一个接受 `item` 作为参数的 Lambda 表达式。

### 6.3 示例 JSON

DSL 表达式: `Self.PP >= Source.Cost && Exists(Self.Field, "item.Attack > 5")`

对应的 JSON 结构:

```json
{
  "type": "BinaryOp",
  "operator": "And",
  "left": {
    "type": "BinaryOp",
    "operator": "GreaterThanOrEqual",
    "left": {
      "type": "ContextAccess",
      "path": ["Self", "PP"]
    },
    "right": {
      "type": "ContextAccess",
      "path": ["Source", "Cost"]
    }
  },
  "right": {
    "type": "FunctionCall",
    "functionName": "Exists",
    "arguments": [
      {
        "type": "ContextAccess",
        "path": ["Self", "Field"]
      },
      { // 嵌套的 item 条件 JSON 对象: item.Attack > 5
        "type": "BinaryOp",
        "operator": "GreaterThan",
        "left": {
          "type": "ContextAccess",
          // "item" 是一个特殊的占位符，表示集合中的当前元素
          // 后端转换逻辑需要能识别并正确处理它
          "path": ["item", "Attack"]
        },
        "right": {
          "type": "IntegerLiteral",
          "value": 5
        }
      }
    ]
  }
}
```

这个 JSON 结构提供了另一种定义条件的方式，与 DSL 等效，并且更适合程序化生成和处理。

## 7. 实现细节 (Sprache 解析、表达式树转换等)

## 7. 实现细节

本节将概述使用 Sprache 解析 DSL、将 AST 转换为 C# 表达式树以及处理 JSON 配置的关键实现步骤和注意事项。

### 7.1 使用 Sprache 解析 DSL

Sprache 是一个基于 Parser Combinator 的库，允许我们用 C# 代码来定义语法的解析规则。

1.  **定义基础解析器 (Parsers):**
    *   `Parse.WhiteSpace`: 定义并忽略空白字符。
    *   `Parse.Identifier`: 解析标识符（如 `Self`, `PP`, `Source`, `Exists`）。
    *   `Parse.Numeric`: 解析整数。
    *   `Parse.StringLiteral`: 解析双引号包围的字符串。
    *   `Parse.BooleanLiteral`: 解析 `true` 或 `false`。
    *   `Parse.EnumLiteral`: 解析 `EnumType.Value` 格式的枚举。需要结合反射或预定义映射来验证枚举类型和值。

2.  **组合解析器构建表达式:**
    *   **优先级处理:** Sprache 通过 `Parse.ChainOperator` 或显式组合（如先解析乘除，再解析加减）来处理运算符优先级。
        *   例如，先定义 `Term`（乘除），再定义 `Expression`（加减）。
    *   **括号处理:** 使用 `Parse.Ref(() => Expression)` 结合括号解析器来处理递归和括号优先级。
    *   **上下文访问:** 解析点 `.` 分隔的标识符序列，构建 `ContextAccessNode`。
    *   **函数调用:** 解析 `FunctionName(Argument1, Argument2, ...)` 结构，构建 `FunctionCallNode`。注意参数列表的解析。
    *   **比较和逻辑运算:** 使用 `Parse.ChainOperator` 定义比较运算符 (`==`, `!=`, `>`, `<`, `>=`, `<=`) 和逻辑运算符 (`&&`, `||`) 的解析。
    *   **一元运算:** 处理 `!` (Not) 或 `-` (Negate) 等前缀运算符。

3.  **顶层解析器:**
    *   定义一个最终的 `ConditionParser`，它组合了所有子解析器，并能解析完整的 DSL 字符串，返回根 `IExpressionNode`。
    *   需要处理输入的结尾 (`Parse.End`)，确保整个字符串都被成功解析。

4.  **错误处理:** Sprache 会在解析失败时抛出异常，提供错误位置和期望的信息。需要捕获这些异常并向用户或日志系统报告有意义的错误信息。

5.  **嵌套条件处理 (针对 `Exists`, `Count`, `All`):**
    *   这些函数的第二个参数是字符串形式的嵌套 DSL。
    *   在解析函数调用时，将这个字符串参数解析为 `StringLiteralNode`。
    *   **关键:** 在后续的 AST 转换阶段，需要**递归调用** `ConditionParser` 来解析这个字符串字面量的值，生成嵌套的 AST，并将其用于构建相应的 Lambda 表达式。

### 7.2 AST 到 C# 表达式树的转换

这一步是将解析得到的 AST 转换为 `System.Linq.Expressions.Expression` 对象。这是一个递归过程，每个 AST 节点类型都有对应的转换逻辑。

1.  **转换器类:** 创建一个 `AstToExpressionConverter` 类，包含一个核心的 `ConvertNode(IAstNode node, ParameterExpression contextParameter)` 方法。`contextParameter` 是一个 `ParameterExpression`，代表传入的 `ConditionContext` 实例。

2.  **节点转换逻辑:**
    *   **Literal Nodes:** 转换为 `Expression.Constant()`。对于 `EnumLiteralNode`，需要使用 `Enum.Parse` 获取实际枚举值。
    *   **ContextAccessNode:**
        *   从 `contextParameter` 开始，根据 `PathSegments` 逐级构建 `Expression.PropertyOrField()` 或 `Expression.Call()`（如果路径中包含方法调用或索引器）。
        *   需要处理类型转换（如 DSL 中的 `(Event as DamageEvent)`），这可以通过 `Expression.TypeAs()` 或 `Expression.Convert()` 实现。需要仔细处理类型信息和可能的 null 值。
        *   对于 `item` 这种特殊标识符（用于集合函数内部），需要传入代表当前项的 `ParameterExpression` 进行转换。
    *   **BinaryOperatorNode:** 根据 `OperatorType` 调用相应的 `Expression` 工厂方法，如 `Expression.Add()`, `Expression.Equal()`, `Expression.AndAlso()` 等，递归转换左右子节点。
    *   **UnaryOperatorNode:** 调用 `Expression.Not()` 或 `Expression.Negate()`，递归转换操作数。
    *   **FunctionCallNode:**
        *   查找与 `FunctionName` 对应的预定义 C# 方法（通常是 `ConditionContext` 的扩展方法或静态辅助方法）。
        *   递归转换所有 `Arguments`。
        *   使用 `Expression.Call()` 构建方法调用表达式。
        *   **特殊处理 `Exists`, `Count`, `All`:**
            *   获取第一个参数（集合表达式）转换后的 `Expression`。
            *   获取第二个参数（字符串字面量），**递归调用** DSL 解析器和转换器，将其转换为一个接受集合元素类型参数（例如 `ParameterExpression itemParam = Expression.Parameter(elementType, "item")`）并返回 `bool` 的 Lambda 表达式 (`Expression<Func<ElementType, bool>>`)。
            *   调用 `System.Linq.Enumerable` 中对应的扩展方法（如 `Any`, `Count`, `All`）的 `Expression.Call()`，传入集合表达式和转换后的 Lambda 表达式。

3.  **最终结果:** `ConvertNode` 方法最终返回一个类型为 `bool` 的 `Expression`。

### 7.3 JSON 配置处理

处理 JSON 配置相对直接，因为它已经具备结构化的信息。

1.  **反序列化:** 使用 `System.Text.Json` 或 `Newtonsoft.Json` 将 JSON 字符串反序列化为对应的 C# DTO 类（这些 DTO 类结构应与 6.2 中定义的 JSON 结构匹配）。

2.  **DTO 到表达式树转换:** 创建一个 `JsonToExpressionConverter`（或者在 `AstToExpressionConverter` 中添加处理 DTO 的逻辑）。这个转换过程与 AST 转换类似，但输入是 DTO 对象而不是 AST 节点。
    *   根据 DTO 的 `type` 字段和其它属性，直接构建相应的 `Expression` 对象。
    *   处理上下文访问、运算符、函数调用等逻辑与 AST 转换类似。
    *   处理嵌套的 JSON 条件（如 `Exists` 的第二个参数）时，递归调用 JSON 转换逻辑。

### 7.4 编译与缓存

1.  **编译:** 无论是从 DSL 还是 JSON 转换得到的最终 `Expression<Func<ConditionContext, bool>>`，调用其 `Compile()` 方法生成可执行的委托 `Func<ConditionContext, bool>`。

2.  **缓存:**
    *   使用 `ConcurrentDictionary<string, Func<ConditionContext, bool>>` 或类似的线程安全字典来缓存编译结果。
    *   缓存的 Key 可以是原始的 DSL 字符串或规范化后的 JSON 字符串。
    *   在评估条件前，先检查缓存中是否存在对应的委托。如果存在，直接使用；如果不存在，则执行解析/转换、编译，并将结果存入缓存。

### 7.5 运行时评估

1.  获取或构建当前的 `ConditionContext` 实例。
2.  根据卡牌能力定义，获取其条件字符串或 JSON 配置。
3.  查找或生成（并缓存）对应的 `Func<ConditionContext, bool>` 委托。
4.  调用委托，传入 `ConditionContext`，得到 `bool` 结果。

这个实现流程结合了 DSL 的灵活性、JSON 的结构化以及 C# 表达式树的高性能，为条件系统提供了一个强大而高效的基础。
