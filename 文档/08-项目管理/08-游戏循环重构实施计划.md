# 游戏循环与队列处理重构实施计划

## 1. 背景与目标

本文档基于设计文档 [`文档/05-游戏系统/04-01-游戏循环与队列处理设计.md`](文档/05-游戏系统/04-01-游戏循环与队列处理设计.md) ，旨在为 `GameService`、`GameHub` 及相关事件处理流程引入**双队列模式（玩家行动队列 + 事件队列）**的重构工作制定详细的实施步骤。

**核心目标:**

1.  **精确定义行动完成点:** 玩家行动在其引发的所有连锁事件处理完毕后才算完成。
2.  **提升UI实时性:** 在行动完成后，可靠触发手牌可玩性等状态更新。
3.  **有序处理复杂交互:** 清晰、有序地处理事件链。
4.  **改善并发控制:** 分离玩家输入与事件处理，简化并发管理。
5.  **提升代码内聚性:** 将状态修改逻辑从 `GameService` 迁移到更合适的领域实体方法中，由 `IEffectHandler` 协调调用。

## 2. 当前状态与发现 (根据最新设计文档更新)

*   `GameHub` 已初步修改，将玩家请求（如 `PlayCard`, `EndTurn` 等）包装为 `PlayerActionWrapper` 并调用 `GameService.EnqueuePlayerActionAsync` 入队。
*   `GameService` 已添加行动队列 (`_playerActionQueues`)、事件队列 (`_eventQueues`)、处理循环 (`GameProcessingLoopAsync`) 的基本框架和入队逻辑 (`EnqueuePlayerActionAsync`, `EnsureProcessingLoopRunningAsync`)。
*   **效果处理体系已引入:** 项目已引入 `IEffectExecutor`, `IEffectHandler` 接口及部分实现，用于处理具体游戏效果。设计文档明确了由 `Executor` 调度、`Handler` 协调、领域实体执行状态修改并返回事件的模式。
*   **状态修改逻辑需统一:** 当前处理具体游戏效果和修改游戏状态的逻辑，部分可能仍在 `GameService` 的旧方法中，部分已在 `EffectHandler` 实现中。**需要确保所有 `EffectHandler` 都遵循设计模式：调用领域实体方法完成状态修改，并返回实体生成的事件。**

## 3. 重构实施步骤 (根据最新设计文档修订)

**原则:** 遵循小步迭代、文档先行、测试驱动（尽可能）的原则。每一步完成后应进行基本测试和验证。

**阶段一：核心处理循环与事件处理流程整合**

1.  **完善 `GameProcessingLoopAsync` (in `GameService.cs`)**
    *   **目标:** 实现设计文档中描述的核心循环逻辑，并正确集成 `IEventProcessor`。
    *   **步骤:**
        *   实现事件队列优先处理逻辑 (`while eventQueue.TryDequeue`)。
        *   在 `GameProcessingLoopAsync` 中注入 `IServiceScopeFactory` (用于创建 Scoped 依赖，如 `GameContext`)。
        *   在处理事件 (`currentDomainEvent`) 时：
            *   使用 `IServiceScopeFactory` 创建一个新的 Scope。
            *   从 Scope 中解析 `IEventProcessor` 和其他必要的 Scoped 服务（如 `GameContext`）。
            *   调用 `IEventProcessor.ProcessEventAsync(currentDomainEvent, gameContext)`。
            *   将 `ProcessEventAsync` 返回的新领域事件 (`newDomainEvents`) 加入 `eventQueue`。
            *   将 `ProcessEventAsync` 返回的事件 DTO (`resultingDtos`) 通过 `BroadcastEventsAsync` 广播。
        *   实现行动队列处理逻辑 (`if eventQueue.IsEmpty && actionQueue.TryDequeue`)。
        *   调用 `ExecutePlayerActionInitialStepAsync(gameId, actionWrapper, actionContext)`。
        *   将 `actionContext.DomainEvents` 加入 `eventQueue`。
        *   记录 `_currentlyProcessingPlayerActionId`。
        *   实现行动完成与手牌更新逻辑 (`if eventQueue.IsEmpty && actionQueue.IsEmpty && _currentlyProcessingPlayerActionId != null`)。
        *   调用 `UpdateAndBroadcastHandPlayabilityAsync`。
        *   重置 `_currentlyProcessingPlayerActionId`。
        *   实现空闲等待 (`Task.Delay`)。
        *   **关键:** 确保所有对 `GameState` 的读写操作都在 `lock (gameLock)` 块内完成。异步操作（如 `await _eventProcessor.ProcessEventAsync`）必须在锁之外执行，但其使用的 `GameState` 应是锁内获取的快照或通过 `GameContext` 传递。

2.  **调整 `IEventProcessor` 和 `EventProcessor.cs`**
    *   **目标:** 使 `EventProcessor` 聚焦于事件执行、能力触发、调用 `AbilityManager`，并收集返回的事件和 DTO。
    *   **步骤:**
        *   确认 `IEventProcessor.ProcessEventAsync` 返回值符合设计: `Task<(List<IGameEvent> NewDomainEvents, List<GameEventDto> ResultingDtos)>`。
        *   在 `EventProcessor.ProcessEventAsync` 实现中：
            *   注入 `IAbilityManager` 和 `IMapper`。
            *   执行 `currentEvent.ExecuteAsync()` 并收集其返回的直接后续事件。
            *   调用 `IAbilityManager.GetAndExecuteTriggeredAbilitiesAsync(currentEvent, context)` (假设 `AbilityManager` 内部会调用 `Ability.ExecuteEffectsAsync` -> `IEffectExecutor` -> `IEffectHandler` -> `DomainEntity` 并返回所有产生的事件)。
            *   收集 `AbilityManager` 返回的所有事件。
            *   生成 `AbilityTriggeredEvent` 领域事件（如果需要区分能力触发本身）。
            *   转换 `currentEvent` 和其他需要广播的事件 (如 `AbilityTriggeredEvent`) 为 DTO。
            *   返回所有收集到的新领域事件和 DTO。
        *   **审视 `IGameEvent.ExecuteAsync`:** 确认其职责。理想情况下，它应只包含事件自身的逻辑（如果需要）并返回直接由该事件产生的后续事件，而不是修改外部状态或调用效果执行器。

3.  **实现 `ExecutePlayerActionInitialStepAsync` (in `GameService.cs`)**
    *   **目标:** 实现设计文档中的逻辑，进行最小化验证和状态变更（如扣除PP），并生成初始领域事件。
    *   **步骤:**
        *   根据 `actionWrapper.ActionType` 进行 `switch`。
        *   执行必要的最小化验证（如回合、阶段、PP是否足够等）。
        *   执行最小化状态变更（例如，扣除出牌所需的PP）。**注意：** 这一步的状态变更应直接在 `GameState` 或 `PlayerState` 上进行，并可能需要生成相应的事件（如 `PpUpdateEvent`）。
        *   创建对应的 **初始领域事件** (e.g., `CardPlayedEvent`, `AttackDeclaredEvent`, `TurnEndedEvent`, `UnitEvolvedEvent`, `MulliganCompletedEvent`)。这些事件代表行动的直接结果，需要包含必要的信息供后续处理。
        *   将创建的初始事件（以及状态变更产生的事件）添加到传入的 `actionContext.DomainEvents` 中。

4.  **定义或确认初始领域事件 (in `CoreGameEvents.cs` 或相关文件)**
    *   **目标:** 确保存在代表玩家行动直接结果的事件。
    *   **步骤:**
        *   确认或创建以下事件（或类似事件），确保它们包含处理所需的所有信息：
            *   `CardPlayedEvent(Guid playerId, CardInstance playedCard, ...)`
            *   `AttackDeclaredEvent(Guid playerId, CardInstance attacker, ICard target, ...)`
            *   `TurnEndedEvent(Guid playerId)`
            *   `UnitEvolvedEvent(Guid playerId, CardInstance evolvedUnit, ...)`
            *   `MulliganCompletedEvent(Guid playerId, List<CardInstance> keptCards, List<CardInstance> drawnCards)`
        *   这些事件的 `ExecuteAsync` 方法应尽可能保持简单，主要用于触发直接的、固定的后续事件（如 `CardPlayedEvent` 可能触发检查 Fanfare 能力的逻辑），而不是包含复杂的状态修改或效果执行。

5.  **实现 `UpdateAndBroadcastHandPlayabilityAsync` (in `GameService.cs`)**
    *   **目标:** 在行动链完成后，计算并推送手牌可玩性。
    *   **步骤:**
        *   获取指定玩家的手牌。
        *   为手牌中的每张卡调用 `CheckPlayabilityCoreLogicAsync` (需要提取或重构 `CheckCardPlayabilityAsync`)。
        *   构建 `HandPlayabilityUpdateDto` (注意 Key 为 `CardInstance.InstanceId` - Guid)。
        *   通过 `_hubContext` 将 DTO 推送给特定玩家或游戏组。

**阶段二：状态修改逻辑迁移与验证**

6.  **迁移 `GameService` 中的状态修改逻辑**
    *   **目标:** 将分散在 `GameService` 旧行动方法（如 `PlayCardAsync`, `AttackAsync` 等）及其辅助方法中的具体状态修改逻辑，由 `EffectHandler` 初步调用，具体细节实现迁移到相应的领域实体方法 (`CardInstance`, `PlayerState`) 。
    *   **步骤 (示例 - 伤害处理):**
        *   定位 `GameService` 中处理伤害计算、生命值修改、检查死亡的代码。
        *   将伤害计算和生命值修改逻辑移入 `CardInstance.TakeDamage(int amount)` 方法，确保该方法返回包含 `DamageEvent` 和可能的 `CardDestroyedEvent` 的列表。
        *   在 `DamageEffectHandler.ApplyAsync` 中，调用 `target.TakeDamage(amount)` 并收集返回的事件。
        *   移除 `GameService` 中的旧伤害处理代码。
    *   **步骤 (示例 - 抽卡处理):**
        *   定位 `GameService` 中处理从牌库取卡、加入手牌、处理牌库空/手牌满的代码。
        *   将这些逻辑移入 `PlayerState.DrawCards(int count)` 方法，确保该方法返回包含 `CardDrawnEvent` (可能多个) 和可能的 `DeckEmptyEvent` 或 `HandFullEvent` 的列表。
        *   在 `DrawCardEffectHandler.ApplyAsync` 中，调用 `targetPlayer.DrawCards(count)` 并收集返回的事件。
        *   移除 `GameService` 中的旧抽卡处理代码。
    *   **重复此过程**，逐步迁移其他效果（召唤、移动、Buff、进化等）的状态修改逻辑。
    *   **验证:** 确保每个 `EffectHandler` 都遵循设计模式，最终调用领域实体方法完成状态修改并返回事件。

7.  **领域实体方法实现与事件生成**
    *   **目标:** 确保所有被 `EffectHandler` 调用的领域实体方法都正确实现了状态修改逻辑，并返回了准确的领域事件列表。
    *   **步骤:**
        *   检查 `CardInstance` 中的方法（如 `TakeDamage`, `Heal`, `ApplyBuff`, `RemoveBuff`, `Evolve`, `AddKeyword`, `RemoveKeyword`, `SetStats` 等）。
        *   检查 `PlayerState` 中的方法（如 `ModifyPp`, `ModifyEp`, `DrawCards`, `DiscardCard`, `AddCardToHand`, `RemoveCardFromHand`, `MoveCardToZone` (如 `DestroyUnit`, `BanishUnit`) 等）。
        *   确保这些方法内部逻辑正确，边界条件处理得当（如伤害不超过致死、治疗不超过上限、PP/EP 不为负等）。
        *   确保方法在修改状态后，创建并返回了所有相关的 `IGameEvent`。

8.  **全面测试与集成**
    *   **目标:** 验证整个重构后的游戏循环、事件处理和效果执行流程是否按预期工作。
    *   **步骤:**
        *   编写或更新单元测试，覆盖 `GameService` 的处理循环逻辑、`EventProcessor`、`AbilityManager`、`EffectExecutor`、`EffectHandler` 和领域实体方法。
        *   进行集成测试，模拟完整的玩家行动（出牌、攻击、结束回合等），检查事件是否正确生成、传递和处理，状态是否正确更新，UI 反馈（特别是手牌可玩性）是否及时准确。
        *   进行端到端测试，通过客户端或模拟客户端与服务器交互，验证游戏流程。
