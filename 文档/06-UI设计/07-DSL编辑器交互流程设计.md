# 07. DSL编辑器交互流程设计

**版本: 1.0**

**作者: AI 技术总监**

**更新日期: 2025-08-25**

## 1. 概述

本文档定义了DSL编辑器在能力创建界面中的宏观交互模式和核心工作流程。它旨在为前端开发人员提供一个清晰的、关于用户如何与系统交互以构建复杂DSL表达式的实现蓝图。

本文档与 `04-DSL节点类型与操作总览.md` 互为补充，前者关注宏观交互，后者关注微观节点行为。

## 2. 核心设计原则

为了提供一个既强大又易于管理的编辑体验，我们确立了以下四个核心设计原则：

1.  **单例编辑工作区 (Singleton Editing Workspace)**
2.  **上下文驱动的类型约束 (Context-Driven Type Constraints)**
3.  **表达式的递归组合 (Recursive Composition)**
4.  **保存时验证 (Save-Time Validation)**

## 3. 详细设计

### 3.1. 单例编辑工作区

- **描述**: 整个能力创建界面中，只存在**一个**全局的、浮动的DSL编辑工作区（例如一个模态框或侧边栏）。
- **机制**:
    - 界面上有多个独立的“DSL输入框”。每个输入框都存储着它自己的DSL表达式数据（AST）。
    - 当用户点击任何一个“DSL输入框”时，该输入框的表达式数据（AST）和它的`expectedType`会被加载到**全局的单例工作区**中进行编辑。
    - 在工作区中完成编辑并保存后，结果会写回到最初点击的那个“DSL输入框”中。
- **效果**: 这种模式避免了在界面上同时渲染多个复杂编辑器的性能问题，并提供了一个专注的编辑环境。

### 3.2. 上下文驱动的类型约束

- **描述**: 每个“DSL输入框”的用途是预先定义好的，因此它对表达式的返回类型有明确的约束。
- **实现**: 在UI组件层面，每个“DSL输入框”都需要一个`expectedType`属性来声明它所接受的返回类型。例如：
    - **目标选择器**中的表达式输入框：`<DslInput expectedType="List<CardInstance>" />`
    - **条件**中的表达式输入框：`<DslInput expectedType="Boolean" />`
    - **效果参数**中的表达式输入框：`<DslInput expectedType="Int32" />`

### 3.3. 表达式的递归组合

- **描述**: DSL中的每一个“值”本身都可以是一个完整的子表达式。编辑器必须支持这种**递归的、分层的表达式构建**。
- **机制**:
    1. **表达式插槽 (Expression Slot)**: 在UI中，任何需要值的地方（如操作符的右操作数、函数的参数），都会被渲染成一个“表达式插槽”。
    2. **激活工作区**: 点击一个“表达式插槽”，会激活**全局的单例编辑工作区**，并将该插槽的`expectedType`传递给工作区。
    3. **独立构建**: 用户在工作区中独立地、从头开始构建一个新的子表达式。
    4. **保存与封装**: 当这个子表达式被保存时，工作区关闭，该子表达式的AST被存入它所来源的“表达式插槽”中。在UI上，这个已完成的子表达式会被渲染成一个紧凑的、带括号的“胶囊”，以表示其封装性。

### 3.4. 保存时验证

- **描述**: DSL编辑器在用户编辑过程中**不进行实时**的最终返回类型校验。校验逻辑被推迟到用户点击“保存”按钮时触发。
- **机制**: 每个“DSL输入框”都会为编辑器提供一个**期望返回类型**（`expectedType`）。点击保存时，编辑器会根据类型推断规则，计算当前表达式的最终返回类型，并与`expectedType`进行比较。
- **结果**:
    - 如果类型匹配，表达式被标记为**有效**。
    - 如果不匹配，会向用户显示一个明确的错误提示（例如：“条件表达式需要返回布尔值，但当前返回的是数值”），但表达式的当前状态（AST）**依然会被保存**，并被标记为**无效**。UI上应有清晰的视觉提示（如红色边框）来标识无效的表达式。
