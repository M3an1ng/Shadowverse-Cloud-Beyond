# 元数据驱动UI架构设计

## 1. 概述

为了支持功能强大且易于扩展的可视化能力编辑器，我们采用了一种元数据驱动的后端架构。该架构的核心思想是，后端通过扫描代码库，自动发现所有可供编辑器使用的构建块（如效果、DSL函数、事件触发器等），并将它们的元数据（如名称、描述、参数等）通过API暴露给前端。

这种方法有以下优点：
- **高扩展性**: 当需要添加新的功能时，开发者只需创建新的实现类并添加相应的元数据标注（Attribute），无需修改任何现有代码，编辑器即可自动支持。
- **单一事实来源 (Single Source of Truth)**: 所有UI所需的信息都直接来源于代码本身，避免了文档与实现之间的脱节。
- **解耦**: 前端UI与后端游戏逻辑完全解耦，前端只需关心如何渲染元数据，后端则专注于实现游戏逻辑。

本文档将详细描述该架构中各个子系统的设计与实现，并将随着系统的迭代而持续更新。

## 2. 效果 (Effect) 元数据系统 (已完成)

这是元数据系统的第一个实现，用于解决 `EffectType` 与其具体实现 (`Handler`) 和参数 (`Params`) 之间的映射问题。

### 2.1. 核心组件

- **`[EffectHandler(EffectType)]` Attribute**: 一个自定义Attribute，用于直接标记在 `EffectHandler` 的实现类上，明确声明该类负责处理哪一个 `EffectType`。
- **`IEffectHandler<TParams>` 泛型接口**: 所有 `Handler` 都必须实现的接口。通过解析这个接口的泛型参数 `TParams`，我们可以自动找到与 `Handler` 对应的 `Params` 类。
- **`IEffectHandlerRegistry` 服务**: 一个在程序启动时运行的单例服务。它负责扫描、发现并缓存 `EffectType` -> (`Handler` 类型, `Params` 类型) 的映射关系。
- **`EffectUIMetadataService` 服务**: 负责生成最终提供给UI的元数据。它会使用 `IEffectHandlerRegistry` 来获取映射关系，然后进一步通过反射读取 `Params` 类中被 `[EffectParameter]` 标记的属性，生成详细的参数信息。

### 2.2. 工作流程

```mermaid
graph TD
    A[程序启动] --> B(EffectHandlerRegistry 初始化);
    B --> C{扫描所有程序集};
    C --> D[查找所有 EffectHandler 实现类];
    D --> E{读取 Handler 上的 [EffectHandler] Attribute};
    E --> F[获取 EffectType];
    D --> G{解析 Handler 的 IEffectHandler<T> 接口};
    G --> H[获取 Params 类型 T];
    F & H --> I[建立 EffectType -> Handler, Params 的映射];
    I --> J(缓存映射字典);

    subgraph "API请求 (通过聚合端点)"
        K[GET /api/AbilityEditorMetadata] --> L(AbilityEditorMetadataController);
        L --> M(AbilityEditorMetadataService);
        M --> M1(EffectUIMetadataService);
        M1 --> N{查询 EffectHandlerRegistry};
        N --> O[获取所有已注册的 EffectType 及其 Params 类型];
        O --> P{反射读取 Params 类的属性};
        P --> Q[读取 [EffectParameter] Attribute];
        Q --> R[生成详细的参数元数据 DTO];
        R --> S(返回 JSON 给前端);
    end

    subgraph "游戏逻辑执行"
        T(EffectExecutor) --> U{查询 EffectHandlerRegistry};
        U --> V[根据 EffectType 获取 Handler 类型];
        V --> W[从DI容器获取 Handler 实例];
        W --> X[执行 Handler 逻辑];
    end
```

## 3. DSL 元数据系统 (已完成)

该系统负责为能力编辑器中的动态值表达式（DSL）提供可用的函数和上下文对象信息。

### 3.1. 核心组件

- **`IFunctionDefinition` 接口**: 所有DSL函数都必须实现的接口。该接口本身就包含了函数的描述、参数等元数据信息。
- **`IFunctionRegistry` 服务**: DSL函数注册表，是所有可用函数的“单一事实来源”。
- **`[DslExposable]` Attribute**: 一个自定义Attribute，用于标记可以在DSL表达式中作为上下文访问的类（如 `PlayerState`, `CardInstance` 等）。
- **`DslMetadataService` 服务**: 在程序启动时运行的单例服务。它采用**混合策略**来收集元数据：
    1. **查询服务**: 它直接查询 `IFunctionRegistry` 服务，获取所有已注册的DSL函数及其元数据。
    2. **反射扫描**: 它扫描程序集，查找所有被 `[DslExposable]` 标记的类，并将它们的公共属性作为可访问的上下文变量。

### 3.2. 工作流程

```mermaid
graph TD
    subgraph "启动时扫描"
        A[程序启动] --> B(DslMetadataService 初始化);
        B --> C{查询 IFunctionRegistry};
        C --> D[获取所有 Function 定义];
        B --> E{扫描所有程序集};
        E --> F[查找所有带 [DslExposable] 的类];
        F --> G[获取所有公共属性];
        D & G --> H[构建并缓存DSL元数据DTO];
    end

    subgraph "API请求 (通过聚合端点)"
        I[GET /api/AbilityEditorMetadata] --> J(AbilityEditorMetadataController);
        J --> K(AbilityEditorMetadataService);
        K --> K1{读取 DslMetadataService 缓存};
        K1 --> L[返回包含所有函数和上下文对象的 JSON];
    end
```

## 4. 事件 (Event) 元数据系统 (已完成)

该系统旨在为能力的触发器 (`TriggerConfig`) 提供一个可供选择的游戏事件列表。

### 4.1. 核心组件

- **`[GameEventMetadata]` Attribute**: 用于标记代表游戏事件的类。该Attribute包含UI显示的名称、描述以及关联的 `EventType` 枚举。
- **`[GameEventParameter]` Attribute**: 用于标记事件类中的关键属性，为UI提供关于事件上下文参数（如“攻击者”、“目标卡牌”）的元数据。
- **`EventMetadataService`**: 一个单例服务，在程序启动时扫描所有被 `[GameEventMetadata]` 和 `[GameEventParameter]` 标记的事件及其属性，并缓存它们的元数据。

### 4.2. 工作流程

```mermaid
graph TD
    subgraph "启动时扫描"
        A[程序启动] --> B(EventMetadataService 初始化);
        B --> C{扫描所有程序集};
        C --> D[查找所有带 [GameEventMetadata] 的事件类];
        D --> E[读取 Attribute 中的元数据];
        E --> F[构建并缓存事件元数据DTO列表];
    end

    subgraph "API请求 (通过聚合端点)"
        G[GET /api/AbilityEditorMetadata] --> H(AbilityEditorMetadataController);
        H --> I(AbilityEditorMetadataService);
        I --> I1{读取 EventMetadataService 缓存};
        I1 --> J[返回所有可用事件的 JSON];
    end
```

## 5. 查询操作 (Query Operation) 元数据系统 (已完成)

该系统旨在为 `TargetConfig` 的UI构建提供所有可用的**查询操作**类型（如“筛选”、“排序”、“提取前N个”）。当用户在目标选择器中添加一个操作步骤时，UI将从此元数据中获取可用的操作列表。

### 5.1. 核心组件

- **`[QueryOperationMetadata]` Attribute**: 一个新的Attribute，用于标记 `IQueryOperation` 的实现类。该Attribute将包含：
    - `DisplayName` (string): 在UI中显示的友好名称，例如“筛选卡牌”。
    - `Description` (string): 对该操作的详细描述。
- **`QueryOperationMetadataService`**: 一个新的单例服务，在程序启动时扫描所有被 `[QueryOperationMetadata]` 标记的类，并缓存它们的元数据。

## 6. 顶层能力编辑器元数据API (已完成)

为了极大简化前端的开发流程，我们创建了一个顶层的聚合API端点，它将一次性返回前端构建完整能力编辑器所需的所有元数据。

### 6.1. 设计思路

- **`AbilityEditorMetadataService`**: 一个新的单例服务，它将注入其他所有元数据服务（`EffectUIMetadataService`, `DslMetadataService`, `EventMetadataService`, `QueryOperationMetadataService`）。
- **`AbilityEditorMetadataController`**: 提供一个统一的 `GET /api/AbilityEditorMetadata` 端点。当被调用时，它会委托 `AbilityEditorMetadataService` 分别调用其他服务，将所有结果聚合成一个单一、巨大的JSON对象返回给前端。

### 6.2. 最终聚合架构图

```mermaid
graph TD
    subgraph "前端 (UI Editor)"
        UI[能力编辑器UI]
    end

    subgraph "后端 (Server)"
        subgraph "API Layer"
            Controller[AbilityEditorMetadataController];
        end
        
        subgraph "Service Layer"
            Aggregator[AbilityEditorMetadataService];
            Service1[EffectUIMetadataService];
            Service2[DslMetadataService];
            Service3[EventMetadataService];
            Service4[QueryOperationMetadataService];
        end

        subgraph "Domain Layer (Code with Attributes)"
            Domain1[Effect Handlers with [EffectHandler]];
            Domain2[DSL Functions & Context Objects with [DslExposable]];
            Domain3[Event Classes with [GameEventMetadata]];
            Domain4[Query Operations with [QueryOperationMetadata]];
        end
    end

    UI -- "GET /api/AbilityEditorMetadata" --> Controller;
    Controller -- "调用" --> Aggregator;
    Aggregator -- "聚合数据" --> Service1;
    Aggregator -- "聚合数据" --> Service2;
    Aggregator -- "聚合数据" --> Service3;
    Aggregator -- "聚合数据" --> Service4;
    
    Service1 -- "扫描" --> Domain1;
    Service2 -- "扫描" --> Domain2;
    Service3 -- "扫描" --> Domain3;
    Service4 -- "扫描" --> Domain4;

```

  "events": [ /* from EventMetadataService */ ],
