# 02. 可视化DSL编辑器原型设计

**版本: 1.0**

**作者: AI 技术总监**

**更新日期: 2025-08-11**

## 1. 概述

本文档旨在为“卡牌能力DSL”设计一个可视化的、基于节点的编辑器界面。此举的核心目标是取代手动编写易错的文本表达式，通过图形化的交互引导用户构建出合法且强大的逻辑，从而极大地降低能力配置的门槛并提升效率。

该编辑器将作为一个独立的、可复用的组件，在所有需要输入DSL表达式的场景（如能力编辑器中的`条件`、`目标`等字段）被调用。

设计将严格遵循《卡牌能力DSL开发指南》中定义的语法和上下文变量。

---

## 2. 核心交互流程

编辑器的核心是一个“上下文感知”的逐步构建流程。用户从一个根节点开始，通过点击和选择，一步步地“生长”出完整的逻辑树。最终，这个可视化的树结构会被序列化成后台可以执行的DSL字符串。

### 2.1. 交互示例：构建 `player.pp >= 7`

以下流程图详细展示了用户构建一个完整条件表达式的全过程：

```mermaid
graph TD
    subgraph "构建表达式: player.pp >= 7"
        A[开始: 空白表达式] --> B["[+] 添加节点"];

            B --> C{弹出选项<br>1. 玩家<br>2. 对手<br>3. 当前卡牌<br>4. ...};
            C -- 用户选择'玩家' --> D["[玩家] 节点已添加"];
        end

        subgraph "步骤 2: 选择属性"
            D --> E["[玩家] [+]"];
            E --> F{弹出选项<br>1. PP<br>2. EP<br>3. 手牌<br>4. 战场<br>5. ...};
            F -- 用户选择'PP' --> G["[玩家].[PP] 节点已添加"];

        subgraph "步骤 3: 选择操作符"
            G --> H["[玩家].[PP] [+]"];
```

### 2.2. 流程说明

1.  **起点**: 用户面对一个空的表达式输入区，只有一个 `[+]` 按钮。
2.  **选择根节点**: 点击 `[+]`，系统会弹出一个上下文菜单，列出所有顶级的DSL关键字（`player`, `opponent`, `self` 等）的中文友好名称。用户选择“玩家”。
3.  **链式选择**: 界面上出现一个表示“玩家”的节点，后面跟着一个新的 `[+]` 按钮。点击它，弹出的菜单会**智能地**只列出 `PlayerState` 对象拥有的所有属性（“PP”, “手牌”, “战场”等）。用户选择“PP”。
4.  **选择操作**: 界面更新为 `[玩家].[PP]` 节点，后面再次出现 `[+]`。此时，由于 `PP` 是一个数字类型，弹出的菜单会变为所有合法的**比较操作符**（`>=`, `==`, `!=`, `<` 等）。用户选择 `>=`。
5.  **输入最终值**: 界面变为 `[玩家].[PP] [>=] [?]`。`[?]` 是一个占位符，提示用户需要输入一个值。用户点击它，它会变成一个数字输入框，用户输入 `7`。
6.  **完成**: 表达式构建完成。在UI的背后，系统已经生成了字符串 `"player.pp >= 7"`。用户可以继续点击 `[+]` 添加 `and` 或 `or` 来构建更复杂的逻辑。

## 3. 节点库与UI设计

为了支撑可视化的构建流程，我们需要定义一个清晰、可扩展的节点库。

### 3.1. 节点类型

我们将定义几种基础的节点类型，每种类型在UI上都有其独特的表现形式：

*   **对象节点 (Object Node)**: 代表一个数据实体，如“玩家”、“当前卡牌”。
    *   **UI**: 通常是一个圆角矩形，包含其中文名称。它是逻辑链的起点。
*   **属性节点 (Property Node)**: 代表一个对象的属性，如“PP”、“手牌”。
    *   **UI**: 附加在对象节点之后，通过 `.` 连接，形成如 `[玩家].[PP]` 的视觉效果。
*   **操作节点 (Operator Node)**: 代表一个操作，如 `>=`、`==`、`and`。
    *   **UI**: 通常用不同的形状或颜色表示（如菱形），清晰地表达逻辑关系。
*   **值节点 (Value Node)**: 代表一个具体的值，如数字 `7` 或字符串 `"Follower"`。
    *   **UI**: 是逻辑链的终点，通常表现为一个可编辑的输入框。
*   **函数节点 (Function Node)**: 代表一个内置函数，如 `Count()`、`IsEmpty()`。
    *   **UI**: 类似于操作节点，但可能包含用于传入参数的“插槽”。

---

### 3.2. 函数节点的链式构建与数据映射

与对象和属性的单向链式构建不同，函数节点（如 `if(condition, then, else)`）引入了“嵌套”的概念。其交互和数据映射遵循以下原则：

1.  **生成参数“插槽”**: 当用户选择一个函数（如“如果”）时，UI会根据从后端获取的元数据，动态生成该函数所需的所有参数“插槽”。每个插槽都是一个全新的、独立的表达式构建起点。
    *   **UI示例**: `如果 (` `[+] condition` `,` `[+] thenValue` `,` `[+] elseValue` `)`

2.  **嵌套构建**: 用户可以点击任何一个参数插槽（如 `[+] condition`），在其中开始一个完整的、独立的子表达式链式构建流程（如构建 `player.pp >= 7`）。

3.  **从UI到DSL的转换**: 当用户完成构建后，前端会执行“序列化”操作，将嵌套的UI结构转换回线性的DSL文本。
    *   **依据**: 此转换过程**严格依赖**后端提供的函数元数据，特别是**参数的顺序和名称**。
    *   **过程**: 前端会按照元数据定义的参数顺序，依次获取每个插槽中子表达式的DSL文本，然后用逗号拼接，最后用函数名和括号包裹，生成最终的字符串：`"if(player.pp >= 7, 1, 0)"`。

这个“元数据驱动的嵌套构建”模型，是连接直观UI与严谨DSL语法的核心桥梁。

## 4. 后端支持：混合元数据生成策略

为了同时支持对**上下文对象（如`PlayerState`）**和**内置函数（如`if`）**的解析，后端将采用一种混合的元数据生成策略。

### 4.1. 核心架构与流程

```mermaid
graph TD
    subgraph "阶段一: 服务器启动时 (仅执行一次)"
        A[服务器启动] --> B[DslMetadataService 初始化];
        
        subgraph "元数据源"
            C1[<b>源1: 反射扫描</b><br>扫描被[DslExposable]标记的<br>上下文类/属性]
            C2[<b>源2: 查询服务</b><br>从IFunctionRegistry服务<br>获取所有已注册的函数定义]
        end

        B --> C1;
        B --> C2;

        C1 --> D[构建上下文元数据];
        C2 --> E[构建函数元数据];

        D & E --> F[在内存中合并并缓存<br>完整的DSL元数据];
    end

    subgraph "阶段二: API 请求时 (每次调用)"
        G[前端请求 GET /api/dsl/metadata] --> H[API 控制器];
        H -- "直接从内存读取 (极快)" --> I[获取已缓存的元数据];
        I --> J[返回统一的JSON给前端];
    end

    J --> K[可视化DSL编辑器UI];

    style A fill:#D6EAF8,stroke:#3498DB
    style G fill:#D5F5E3,stroke:#2ECC71
```

### 4.2. 实现步骤

1.  **丰富函数定义**: (架构重构)
    *   扩展 `IFunctionDefinition` 接口，为其增加 `Description` 和 `Parameters` (一个结构化列表) 属性。
    *   更新所有现有的函数类（如 `IfFunction`），让它们明确提供自己的描述和参数信息。这是确保前端能正确生成UI和转换DSL文本的**关键前提**。

2.  **定义`[DslExposable]`特性**:
    *   创建一个自定义特性，用于标记所有希望暴露给DSL编辑器的**上下文对象类及其属性**（如 `PlayerState`, `CardInstance`）。该特性将包含 `DisplayName` 和 `Description`。

    ```csharp
    [AttributeUsage(AttributeTargets.Class | AttributeTargets.Property | AttributeTargets.Method)]
    public class DslExposableAttribute : Attribute
    {
        public string DisplayName { get; }
        public DslExposableAttribute(string displayName)
        {
            DisplayName = displayName;
        }
    }
    ```

2.  **标记数据模型**:
    遍历 `PlayerState.cs`, `CardInstance.cs` 等所有DSL中用到的领域模型文件，为需要暴露的类和属性打上该特性。

    ```csharp
    [DslExposable("玩家状态")]
    public class PlayerState
    {
        [DslExposable("当前PP")]
        public int CurrentPlayPoints { get; /*...*/ }
        
        [DslExposable("手牌列表")]
        public List<CardInstance> Hand { get; /*...*/ }
    }
    ```

3.  **实现`DslMetadataService`单例服务**:
    这个服务将作为**单例 (Singleton)** 在服务器启动时被依赖注入容器创建。
    *   **构造函数**: 在其构造函数中，执行**一次性**的元数据构建工作：
        1.  注入 `IFunctionRegistry` 服务，遍历所有已注册的函数，将它们的信息转换为函数元数据。
        2.  执行对所有相关程序集的反射扫描，查找 `[DslExposable]` 特性，构建上下文对象元数据。
        3.  将两种元数据合并，并存储在一个私有字段中以供缓存。
    *   **公共方法**: 提供一个公共方法，如 `GetDslMetadata()`，该方法直接返回已缓存的完整元数据对象。

4.  **创建API端点**:
    创建API端点 `GET /api/dsl/metadata`。该端点的处理器将注入 `DslMetadataGenerator` 单例服务，并调用其 `GetMetadata()` 方法，然后将结果序列化为JSON返回。由于只是从内存中读取，此操作性能极高。

### 4.3. 方案优势

*   **高性能**: 通过“启动时扫描，运行时读取缓存”的策略，完美解决了反射的性能问题，确保了API的快速响应。
*   **单一事实来源**: C#源代码是唯一需要维护的地方。
*   **自动化与同步**: 对DSL可用项的任何增删改，都能在下次服务器重启后自动反映到前端编辑器，无需任何手动同步工作。
*   **强类型与安全**: 只有被明确标记了 `[DslExposable]` 的成员才会被暴露，保证了API的安全性。
