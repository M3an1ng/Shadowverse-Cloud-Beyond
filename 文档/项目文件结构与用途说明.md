**作者:** AI 技术总监

## 1. 总体结构概览

## 2. 根目录文件与目录

- **`index.html`**:
  - **用途:** 游戏的主 HTML 文件，定义网页骨架和游戏界面的基本布局。
  - **关键:** 包含对 `style.css` 的链接和对 `src/main.js` 的脚本引用 (`type="module"`).
- **`style.css`**:
  - **用途:** 包含所有的 CSS 规则，负责定义游戏界面的视觉样式和布局。
- **`.gitignore`**:
  - **用途:** 指定 Git 应忽略的文件和目录（例如 `node_modules`, `*.db`, `bin/`, `obj/` 等）。
- **`global.json`**:
  - **用途:** 定义项目使用的 .NET SDK 版本，确保开发环境一致性。
- **`script.js`**:
  - **用途:** **(已废弃)** 旧版单体 JS 文件。**不应再被引用或修改。**
- **`package.json`**:
  - **用途:** **Node.js 项目清单文件**。定义项目元数据（名称、版本等）、依赖项 (`@microsoft/signalr` 等) 和脚本命令。由 `npm init` 创建，由 `npm install` 更新。
- **`package-lock.json`**:
  - **用途:** **精确依赖版本锁定文件**。确保每次安装时都使用完全相同的依赖版本，保证环境一致性。由 `npm install` 自动生成和管理。
- **`/node_modules` 目录**:
  - **用途:** **存放项目依赖包**。包含通过 npm 安装的所有第三方库（如 `@microsoft/signalr` 及其依赖）。此目录通常不提交到版本控制（应在 `.gitignore` 中忽略）。

## 3. `/data` 目录 (原始数据)

存放游戏的核心静态数据，通常在游戏启动时加载。

- **`card_data.json`**:
  - **用途:** **卡牌数据库 (前端原始数据)**。以 JSON 数组格式存储所有卡牌的静态定义信息。在 M4 阶段，后端数据库是主要的数据源，此文件可作为备份或用于无需后端的纯前端测试。
  - **注意:** **M4 后，此文件不再是权威数据源**，主要用于开发和调试。实际卡牌数据由后端 API 提供。

## 4. `/src` 目录 (前端 JS 模块)

存放模块化的 JavaScript (ES Modules) 前端代码。

- **`main.js`**:
  - **用途:** **前端应用入口**。负责导入其他核心模块，初始化游戏 (`gameManager.init()`)，并设置全局事件监听器。
- **`gameManager.js`**:
  - **用途:** **前端游戏状态与流程协调器**。管理前端视图所需的游戏状态（玩家 HP、手牌、战场等），处理用户输入（通过 `ui.js` 转发），调用后端 API 执行游戏动作，并根据后端响应更新前端状态。
- **`turnManager.js`**:
  - **用途:** **前端回合视觉与简单逻辑管理器**。处理前端可见的回合切换效果，可能包含少量纯前端的状态重置（如攻击次数），但核心回合逻辑（抽卡、资源增加）由后端处理。
- **`cardManager.js`**:
  - **用途:** **前端卡牌数据加载与实例管理**。负责从后端 API (`/api/cards`) 获取卡牌定义，并根据需要创建卡牌的前端表示（JS 对象或 DOM 元素）。管理卡牌实例的运行时状态（如当前生命值 - 可能由后端同步）。
- **`player.js`**:
  - **用途:** **前端玩家数据显示模型**。定义 `Player` 类或对象，主要用于存储从后端同步过来的玩家状态（HP, PP, EP, 手牌 ID 列表, 战场卡牌 ID 列表等），方便 UI 渲染。
- **`ui.js`**:
  - **用途:** **UI 渲染与事件处理**。负责所有 DOM 操作，根据 `gameManager` 提供的状态渲染游戏界面 (`renderGame`, `updateHand`, `updateBoard` 等)，处理用户交互事件（点击、拖拽），并将用户意图转发给 `gameManager`。**不包含游戏逻辑**。
- **`ai.js`**:
  - **用途:** **(未来扩展/可选)** AI 逻辑的前端部分，可能用于处理 AI 的动画或简单的非决策性行为。核心 AI 决策逻辑移至后端。

## 5. `/info` 目录 (辅助信息)

存放非运行时必须，但对开发、理解或维护有帮助的辅助信息文件。

- **`keyword.csv`**:
  - **用途:** **关键字参考**。以 CSV 格式列出游戏中的关键字及其 ID、中英文名称和描述。主要供开发者查阅，可能用于文档生成或 UI Tooltips 数据源。

## 5.5 `/Server` 目录 (ASP.NET Core 后端)

存放 ASP.NET Core 后端项目的相关文件。该后端负责处理核心游戏逻辑、状态管理、数据持久化，并通过 Web API 与前端交互。采用分层架构。

- **`/Server/Domain/`**:
  - **用途:** **领域层 (Domain Layer)**。包含核心业务逻辑、领域实体 (`Entities`) 和领域接口 (`Interfaces`)。
  - `Entities/CardDefinition.cs`: 卡牌定义的领域实体。
  - `Interfaces/ICardRepository.cs`: 定义卡牌数据仓库的契约。
- **`/Server/Application/`**:
  - **用途:** **应用层 (Application Layer)**。协调领域层和基础设施层，实现应用服务 (`Services`)，处理应用逻辑和用例。可能包含数据传输对象 (DTOs)。
  - `Services/ICardService.cs`: 卡牌应用服务接口。
  - `Services/CardService.cs`: 卡牌应用服务实现。
  - `Services/IGameService.cs`: 游戏核心逻辑服务接口。
  - `Services/GameService.cs`: 游戏核心逻辑服务实现 (M4 后将包含实际逻辑)。
- **`/Server/Infrastructure/`**:
  - **用途:** **基础设施层 (Infrastructure Layer)**。提供技术实现细节，如数据库访问 (`Data`, `Persistence`)、外部服务集成等。
  - `Data/ApplicationDbContext.cs`: EF Core 数据库上下文。
  - `Data/Migrations/`: EF Core 数据库迁移脚本。
  - `Data/DataSeeder.cs`: 数据库初始数据填充逻辑。
  - `Persistence/EFCardRepository.cs`: `ICardRepository` 的 EF Core 实现。
- **`/Server/Presentation/`**:
  - **用途:** **表示层 (Presentation Layer)**。负责处理 HTTP 请求和响应，定义 Web API 端点 (`Endpoints`)。
  - `Endpoints/CardEndpoints.cs`: (示例) 定义与卡牌相关的 API 端点。
- **`/Server/Properties/`**:
  - **用途:** 存放项目配置，如 [`launchSettings.json`](Server/Properties/launchSettings.json:0)。
- **`/Server/wwwroot/`**:
  - **用途:** 存放静态文件（如 CSS, JS, 图像）。在本项目中，前端文件位于根目录，此目录可能为空或用于存放后端特定的静态资源。
- **`Server.csproj`**: C# 项目文件。
- **`Program.cs`**: 后端应用程序入口与配置中心。
- **`appsettings.Development.json` / `appsettings.json`**: 应用程序配置文件。
- **`shadowverse.db`** (根目录下生成): SQLite 数据库文件。

## 7. 与标准项目结构的差异或缺失的文件说明

为了保持项目简单并专注于核心逻辑，当前结构故意省略或简化了一些标准 Web 项目或更大型 C# 项目中常见的文件/目录：

- **前端相关:**
  - **构建工具配置文件** (如 `webpack.config.js`, `vite.config.js`): 不存在。没有使用前端构建工具。
  - **前端测试框架/文件**: 不存在。目前没有包含单元测试或端到端测试。
- **后端相关:**
  - **单元/集成测试项目**: 不存在。尚未为后端代码添加自动化测试。
  - **API 文档生成配置文件** (如 Swagger/OpenAPI 的详细配置，虽然基础已集成): 可能简化。
  - **`.sln` 解决方案文件**: 不存在。当前只有一个 C# 项目 (`.csproj`)，未使用 Visual Studio 解决方案文件来组织多个项目。
- **通用:**
  - **`Dockerfile` / `docker-compose.yml`**: 不存在。未进行容器化配置。
  - **CI/CD 配置文件** (如 `.github/workflows/`, `azure-pipelines.yml`): 不存在。没有设置持续集成/持续部署流程。

这些缺失的部分可以在项目发展到相应阶段时根据需要逐步引入。
