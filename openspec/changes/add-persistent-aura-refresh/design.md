## Context
The current ability pipeline evaluates TriggerConfig-driven abilities through GameActionTransactionService and AbilityManager. Triggered abilities are indexed by event type (AbilityManager) and evaluated in Before/On/After timing (GameActionTransactionService). Conditions are evaluated by ConditionEvaluator and TargetSelectionService resolves targets without embedding DSL details. Buffs are applied via StatChangedEvent/BuffService, with stacking and identity handled using EffectKey.

Goal: support persistent auras that refresh target sets on explicit events, using the same trigger/condition/target logic as existing DSL abilities.

## Goals / Non-Goals
- Goals:
  - Allow DSL to declare a refreshable aura with explicit refresh triggers (EventType + timing + relation).
  - Reuse existing TriggerConfig, ConditionEvaluator, and TargetSelectionService logic.
  - Apply aura effects as persistent buffs with deterministic identity and safe stacking.
  - Refresh targets on configured events (CardMoved, Transform, etc.) without scanning all auras.
- Non-Goals:
  - Auto-refresh on every event by default.
  - Support player choice targets for aura refresh (refresh must be deterministic).
  - Execute one-shot effects (damage, destroy) from aura refresh.

## Decisions
- Introduce an AuraConfig (or EffectType.AddAura) that stores:
  - RefreshTriggers: TriggerConfig[]
  - Targets: Dictionary<string, TargetConfig>
  - Effects: EffectConfig[]
  - DurationType/DurationParameter/CanStack
- Add AuraManager as a runtime service responsible for registration, refresh evaluation, target diffing, and buff application/removal.
- Refresh triggers are evaluated with the same Trigger.CanTrigger and ConditionEvaluator used by regular abilities, using TriggeringEvent on the GameContext.
- Aura effects are applied as buffs using BuffService, with EffectKey built from (SourceAbilityId, AuraId, TargetId, EffectIndex) to ensure deterministic stacking and removal.
- Restrict aura effects to a safe list (ModifyStatus/SetStatus/SetKeyword/GrantAbility/RemoveBuff) to keep refresh idempotent.

## Data Model
- AuraConfig
  - RefreshTriggers: List<TriggerConfig>
  - TargetConfigs: Dictionary<string, TargetConfig>
  - EffectConfigs: List<EffectConfig>
  - DurationType, DurationParameter, CanStack
- AuraInstance
  - AuraId (Guid), SourceAbilityId (Guid), SourceCardId (Guid?)
  - RefreshTriggers (Trigger runtime wrappers)
  - TargetConfigs, EffectConfigs
  - ActiveTargets: HashSet<Guid> (card instance ids)
  - IsActive

## Runtime Flow
1) Ability triggers and executes AddAura (or registers AuraConfig during activation).
2) AuraManager registers AuraInstance and indexes it by RefreshTriggers.EventTypes.
3) On each game event, GameActionTransactionService (or a dedicated hook) asks AuraManager to evaluate refreshable auras for that EventType and timing.
4) For each matching aura:
   - Evaluate Trigger.CanTrigger using the same relation/zone rules.
   - Evaluate Ability conditions via ConditionEvaluator (no player choice).
   - Resolve targets using TargetSelectionService in non-cancellable mode.
   - Diff target set against ActiveTargets.
   - Apply buffs to new targets; remove buffs from removed targets.

## Refresh Evaluation
- RefreshTriggers are explicit; CardMoved/Transform are not auto-added.
- Auras are indexed by EventType string, matching AbilityManager indexing.
- TriggerTiming is respected; refresh can run on Before/On/After like other abilities.
- RelationType and zone checks reuse Trigger.CanTrigger.

## Buff Application
- Use BuffService.ApplyBuffProcess with composite buff effects.
- EffectKey format: "{SourceAbilityId:N}:{AuraId:N}:{TargetId:N}:{EffectIndex}".
- CanStack honored; non-stackable auras skip if identical EffectKey exists.
- Removal uses BuffService.RemoveBuffsFromSource or EffectKey matching.

## Loop Prevention
- Aura refresh events should not trigger another refresh for the same aura in the same cycle.
- Add a GameContext flag (IsAuraRefresh) or refresh cycle id; AuraManager ignores events generated by itself.
- If DSL explicitly wants BuffApplied/StatChanged as refresh triggers, it must opt-in.

## DSL Integration
- Extend AbilityConfig with AuraConfig list or add EffectType.AddAura with AddAuraEffectParams.
- Extend DSL parser to allow:
  - refresh { on CardMoved after; on Transform after; }
  - targets { ... } and effects { ... } blocks reused from normal abilities.
- Target selection for refresh must be deterministic (SelectionMethod != PlayerChoice).

## Example
- "Allied amulets have Act cost 0 while this source remains."
  - AddAura with RefreshTriggers: CardMoved.After, Transform.After
  - Targets: PlayerScope=Self, CardType=Amulet, Zone=Field
  - Effects: SetStatus(CostModifier=0)

## Risks / Trade-offs
- Incorrect loop guards could cause refresh storms; must be tested with chained buffs.
- Target resolution can be expensive; index by EventType and restrict refresh triggers.
- Some effect types are not safe for reapplication; enforce whitelist.

## Migration Plan
- No data migration required; new DSL fields are optional.
- Existing abilities unchanged.

## Open Questions
- Should AuraConfig live under AbilityConfig or be an EffectType (AddAura)?
- Should aura removal be tied to source card zone change (CardMoved) or ability disable/silence only?
- Should RefreshTriggers default to empty (explicit only) or optional defaults per capability?
