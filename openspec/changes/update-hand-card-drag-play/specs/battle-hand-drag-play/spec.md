## ADDED Requirements

### Requirement: Drag Gesture Activates Hand Card Play
The battle UI SHALL treat drag-to-play as the primary gesture for playing a hand card. A hand-card play gesture SHALL begin only after pointer movement crosses a configured drag threshold, and a pointer interaction that does not cross the threshold SHALL remain a preview-only click.

#### Scenario: Click keeps preview behavior
- **WHEN** the player presses and releases a playable hand card without exceeding the drag threshold
- **THEN** the battle UI updates preview or selection state without submitting a play request

#### Scenario: Drag threshold activates play gesture
- **WHEN** the player moves a playable hand card past the drag threshold during pointer interaction
- **THEN** the battle UI enters hand-card drag mode for that card and no double-click is required to play it

### Requirement: Hand Card Drag Feedback
While a playable hand card is being dragged, the battle UI SHALL provide continuous visual feedback that indicates the dragged card, the original hand slot, and whether the current drop target is valid.

#### Scenario: Drag feedback appears on activation
- **WHEN** hand-card drag mode begins
- **THEN** the battle UI shows a transient dragged-card visual and marks the source hand-card slot as the drag origin

#### Scenario: Invalid drop feedback appears
- **WHEN** the dragged hand card is hovering over a non-playable release area
- **THEN** the battle UI shows invalid drop feedback instead of confirming the play

#### Scenario: Invalid drop snaps back
- **WHEN** the player releases the dragged hand card over an invalid release area
- **THEN** the battle UI returns the dragged card to its hand position and does not submit a play request

### Requirement: Valid Drops Use Existing Play Submission
The battle UI SHALL resolve a valid hand-card drop through the existing `playCard` submission pipeline and SHALL submit at most one play request for each completed drag gesture.

#### Scenario: Valid board-area drop plays card
- **WHEN** the player releases a playable hand card over a valid play area for that card
- **THEN** the battle UI submits exactly one `playCard` request for that hand card

#### Scenario: Release click is suppressed after drag
- **WHEN** a completed hand-card drag resolves on pointer release
- **THEN** the battle UI suppresses the follow-up click generated by the release so the same interaction does not trigger preview or a second play submission

### Requirement: Target-Requiring Cards Preserve Target Resolution Rules
Dragging a hand card that requires targets SHALL preserve the existing target legality and choice flow. The battle UI SHALL submit a direct target only when the release target is a valid immediate target for that card; otherwise it SHALL hand off to the existing player-choice flow.

#### Scenario: Direct target drop submits target
- **WHEN** the player releases a target-requiring hand card over a valid direct target
- **THEN** the battle UI submits the play request with that target identifier

#### Scenario: Non-target drop opens existing choice flow
- **WHEN** the player releases a target-requiring hand card over a valid cast area without a direct valid target
- **THEN** the battle UI submits the card play through the existing pipeline and the later target selection continues through the current `PlayerChoiceRequested` flow

#### Scenario: Invalid target does not bypass legality
- **WHEN** the player releases a target-requiring hand card over an invalid target
- **THEN** the battle UI does not submit a targeted play request and instead treats the interaction as an invalid drop unless another valid release rule applies

### Requirement: Fallback Controls Remain Available
The battle UI SHALL keep a non-drag fallback path for hand-card play and SHALL reduce purely decorative drag motion when reduced-motion preferences are active.

#### Scenario: Action button remains usable
- **WHEN** the player uses the existing hand-card play button instead of dragging
- **THEN** the battle UI submits the same `playCard` flow used before the drag update

#### Scenario: Reduced-motion drag feedback
- **WHEN** the client reports a reduced-motion preference and the player drags a playable hand card
- **THEN** the battle UI uses simplified drag feedback that preserves validity and release-state cues without requiring full motion effects
