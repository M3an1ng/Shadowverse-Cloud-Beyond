# 目标选择系统重构设计 (V2.0 - 简化模型)

## 1. 背景

在修复“天使之箭”目标选择BUG的过程中，我们发现当前基于 `ITargetSelector` 接口和 `SelectorType` 枚举的动态调度设计存在过度复杂的问题。该设计虽然灵活，但对于当前“筛选潜在目标 -> [可选]玩家选择”的核心需求而言，增加了不必要的抽象层次和理解成本。

经过讨论，我们决定对该系统进行重构，以简化设计、提高代码可读性和可维护性为首要目标。

## 2. 核心决策：从动态调度到固定管道

我们决定废弃 `ITargetSelector` 的多态调度模型，将目标选择流程固化为一个职责明确的两阶段管道：

1.  **阶段一：潜在目标筛选 (Potential Target Filtering)**
    *   **职责**：根据卡牌能力配置，从当前游戏状态中筛选出所有符合条件的潜在目标，形成一个“目标池”。
    *   **实现**：此阶段将合并现有 `FilteredTargetSelector` 和 `CompositeTargetSelector` 的功能。

2.  **阶段二：玩家选择验证 (Player Choice Validation)**
    *   **职责**：如果一个能力需要玩家手动选择目标，则在此阶段接收玩家选择的目标ID，并验证该ID是否存在于第一阶段产生的“目标池”中，同时检查选择数量是否满足能力要求（min/max）。
    *   **实现**：此逻辑将作为 `TargetSelectionService` 的一个独立方法存在。

## 3. 架构图 (Mermaid)

```mermaid
graph TD
    A[GameService: CheckPlayability] --> B(TargetSelectionService: GetPotentialTargets);
    B --> C{执行卡牌的DSL查询};
    C --> D[返回所有潜在目标 (目标池)];
    D --> E[前端高亮所有潜在目标];

    subgraph 玩家执行出牌动作
        F[GameService: PlayCard with Target] --> G(TargetSelectionService: ResolvePlayerChoice);
        G --> H{执行卡牌的DSL查询};
        H --> I[获取所有潜在目标 (目标池)];
        I --> J{验证玩家选择是否在目标池内};
        J -- 成功 --> K[返回最终的单个目标];
        J -- 失败 --> L[抛出异常，中断出牌];
    end
```
