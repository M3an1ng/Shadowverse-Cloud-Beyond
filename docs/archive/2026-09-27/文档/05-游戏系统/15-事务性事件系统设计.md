# 事务性事件系统架构设计

## 1. 问题背景与目标

在实现复杂的卡牌能力（如带“战吼”目标选择的随从）时，我们遇到了现有`Effect-Event`架构的根本性瓶颈。当前架构在`EffectHandler`中立即修改游戏状态并生成事件，这导致了在请求玩家进行目标选择时，出牌动作（如支付费用、移动卡牌）已经完成，无法被撤销。

本次重构的核心目标是，在遵循“事件是状态变更的唯一真实依据”原则的前提下，实现一个支持**原子性、可撤销的复杂玩家操作**的事件系统。

## 2. 核心设计原则

1.  **计算与执行分离**: 彻底分离状态变更的“计算”阶段和“执行”阶段。实体类只负责计算变更，而将执行权统一上移。
2.  **事务性与原子性**: 一个完整的玩家动作，包括其所有连锁反应，都应被视为一个单一的事务。它要么完整地发生，要么完全不发生。
3.  **委托驱动**: 将状态变更的具体逻辑（如何修改）封装在委托中，由事件携带，以实现“高内聚，低耦合”。

## 3. 新架构详解：两阶段委托驱动模型

我们将引入一个两阶段的处理流程来替代当前的“立即执行”模型。

### 3.1. 核心概念

*   **暂存事件 (Staged Event)**: 一个描述“将要发生什么”的**数据蓝图**。它在暂存阶段被创建，本身不包含执行逻辑。
*   **可提交事件 (`ICommittableEvent`)**: 一个接口，代表事件已通过所有逻辑验证，是“**待执行的命令**”。它包含一个`Action<GameContext>`类型的委托。
*   **委托 (`CommitAction`)**: 由实体类创建，封装了**如何**修改状态的具体逻辑。它由事件携带，在结算阶段被调用。

### 3.2. 两阶段处理流程

```mermaid
graph TD
    subgraph 阶段一：暂存与模拟 [只读]
        A[玩家动作请求] --> B[EffectHandler];
        B --> C{实体方法: 计算变更};
        C --> D[生成 暂存/可提交事件];
        D --> E[GameService: 收集事件到暂存队列];
        E --> F{递归检查队列: 是否需玩家输入?};
    end

    subgraph 阶段二：结算或撤销 [写入]
        F -- 是 --> G[暂停, 等待玩家输入];
        G -- 玩家取消 --> H[清空暂存队列, 动作撤销];
        G -- 玩家确认 --> I;
        F -- 否 --> I{最终确认};
        I --> J[**结算器: 遍历队列, 执行事件的CommitAction委托**];
        J --> K[**原子性地修改所有实体状态**];
        K --> L[统一广播所有事件DTO];
    end
```

### 3.3. 实体与事件的职责演变

实体类（如`CardInstance`）的方法将不再直接修改状态，而是返回一个`ICommittableEvent`列表。

**示例: `CalculateDamageTaken`**
```csharp
// 接口定义
public interface ICommittableEvent : IDomainEvent
{
    Action<GameContext> CommitAction { get; }
}

// 实体方法实现
public IEnumerable<ICommittableEvent> CalculateDamageTaken(int amount, CardInstance? source = null)
{
    // ... 只读计算 ...
    int actualDamage = ...;

    if (actualDamage > 0)
    {
        // 1. 创建一个封装了修改逻辑的委托
        Action<GameContext> commitLogic = (context) =>
        {
            var cardInState = context.GameState.GetCard(this.InstanceId);
            if (cardInState != null)
            {
                // 真正的状态修改逻辑被封装在这里
                cardInState.Damage += actualDamage;
            }
        };

        // 2. 将事件“蓝图”和“施工队”（委托）一起返回
        yield return new HealthChangedEvent(this, ..., commitLogic);
    }
}
```

## 4. 性能分析

此架构用可控的性能开销，换取了巨大的架构优势。

*   **CPU开销**: 主要新增点在于暂存阶段的“递归检查”。通过优化的字典查询，此开销对于绝大多数游戏操作而言都在亚毫秒级，远低于网络延迟，**影响可忽略**。
*   **内存分配**: 主要新增点在于为每个可提交事件创建委托和闭包。这会**中度增加GC压力**，是主要的性能权衡点。在正常游戏负载下，现代.NET的GC足以应对。若未来性能分析显示此处成为瓶颈，可引入**对象池 (Object Pooling)**作为优化手段。

**结论**: 架构的健壮性、正确性和可扩展性带来的收益，远超其在性能上的微小代价。

## 5. 对录像系统 (Replay System) 的支持

新架构天然是构建一个**100%精确的、基于事件的录像系统**的完美基石。

*   **录像记录**: 系统只需记录两个核心数据：
    1.  **对局的初始状态 (`InitialGameState`)**。
    2.  一个**“已提交事件包” (`CommittedEventBundle`) 的有序列表**。每个包就是一次完整操作最终结算的所有事件集合。

*   **录像回放**:
    1.  加载初始状态。
    2.  按顺序将每个“已提交事件包”喂给一个只执行结算逻辑的回放服务。
    3.  该服务依次执行包中每个事件的`CommitAction`委托。

*   **优势**: 此方法保证了回放的**绝对精确**，且录像文件**数据量小**、**高度结构化**，极易于进行数据分析、AI训练和平衡性测试。
