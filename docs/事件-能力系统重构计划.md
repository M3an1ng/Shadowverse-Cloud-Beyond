# 事件-能力系统重构计划

> 计划日期：2026-09-28  
> 状态：待实施  
> 适用范围：服务端事件事务、卡牌能力触发、事件历史、回放数据、用户级 DSL 配置

## 1. 计划目标

本计划基于当前用户级 DSL 的配置方式，对事件-能力系统做一次边界重构。目标不是增加更多事件类型，也不是把内部架构暴露给卡牌作者，而是固定已有事件的生命周期和数据来源。

完成后应满足：

1. `Before` 保留现有检查、拦截、改写及普通效果的执行规则，包括混合 Before 能力的顺序。
2. `On` 保留“在原有提交前判定点确定触发资格，提交成功后按原队列顺序结算效果”的两阶段语义。已有主能力预检结果继续按原规则复用。
3. `After` 保留现有条件判断、效果准备和入队位置；不把它解释成所有 On 效果执行完成后才开始的统一阶段。
4. 为事件历史、回放 JSON、前端 DTO 和 DSL 历史查询建立统一冻结事实来源；执行上下文与历史读取的切换分别验收。
5. 事件不再因为 `CardInstance` 变身、移动或属性变化而改变历史内容。
6. 普通卡牌 DSL 不需要理解请求事件、内部事件和投影事件的实现细节。
7. 激奏、结晶、爆能继续保持 DSL 可用，并明确为成功出牌后的模式事实。

**业务兼容约束：** 生命周期整理以既有可观察行为等价为准，不以方法名称或流程图相似为准。条件结果、目标、动态数值、事件和效果顺序、触发次数、失败与取消结果均属于业务行为。历史查询由活引用切换为冻结值、普通能力事件权限收紧属于单独的兼容迁移事项，须列出差异并确认后启用，不随 On 整理隐式生效。

## 2. 当前问题与根因

### 2.1 On 的准备与结算职责需要显式区分

当前普通 On 效果的主要流程是：

```text
Before 处理
    -> 匹配 On 能力、检查能力条件
    -> 创建效果请求并按现有顺序入队
    -> Commit
    -> 递归处理提交产生的子事件
    -> 判断 After 能力并准备、入队
    -> 外层调度器按原规则执行效果
```

“提交前准备效果请求”与“提交前实际执行效果”是不同操作。能力级条件读取提交前状态是现有业务规则，不作为本次重构要消除的问题。部分需要玩家选择的主能力会在更早的预检中判断条件并缓存结果，正式处理时继续复用；也不统一迁移到 Before 之后重新判断。

代码基线入口：

- `GameActionTransactionService.AnalyzePrimaryAbilitiesAsync`：主能力选择、决策预检及结果缓存。
- `GameActionTransactionService.GetTriggerAbilityEffectsAsync`、`AbilityManager.ProcessSingleAbilityAsync`：能力匹配、条件检查、预检结果复用及效果准备。
- `Ability.CheckConditions`：按事件复用已求值的条件结果。
- `GameActionTransactionService.ProcessEventRecursivelyAsync`：On 准备和入队先于当前事件 Commit，子事件处理先于当前事件 After 准备。
- `GameActionTransactionService.CommitTransactionAsync`：事件队列优先、效果队列随后推进的调度规则。
- `ResolveDeferredTargetsIfNeededAsync`、`EffectExecutor.ResolveEffectParameters`：保留结算时目标解析和动态参数求值。

同时，`RecordTrigger`、同名触发名额和 `AbilityTriggered` 等关联事件存在既定处理时点及可观察副作用。它们与排队效果分开核对，保留现有顺序和失败记录行为；本次不把所有提交前活动统一后移，也不引入全事务自动回滚。

### 2.2 历史直接保存运行时对象

`IGameEvent` 的 `Source`、`Target` 通过 `TargetInfo` 持有 `CardInstance` 或 `PlayerState`。当前内存历史直接保存原始事件实例，导致历史记录依赖可变实体。

典型漂移场景：

- 出牌后卡牌变身，旧出牌记录显示新定义；
- 卡牌离场后，历史目标的区域变成当前区域；
- 伤害、生命、费用和关键字变化后，旧事件读取到最新值；
- DSL 回查事件时通过当前实体重新解析，得到与当时事实不同的结果。

### 2.3 事件角色没有统一约束

当前请求、事实、内部路由和前端投影事件主要依赖命名与调用位置区分，服务端没有统一的角色策略。前端虽然可以过滤事件，但不能代替服务端的能力权限校验。

## 3. 目标模型

### 3.1 事件生命周期

以下流程针对一个可提交事件；主行动预检和外层队列调度是两个独立层次：

```text
请求展开、主能力预检和现有一致性校验（保持原位置及缓存规则）
    -> 进入现有事件调度
        -> Before：现有拦截、改写及普通效果
        -> On.Prepare：原位置匹配、判断条件或复用既有结果
        -> 原位置准备、入队及处理关联触发记录和事件
        -> Commit：提交当前事件状态变化
        -> Freeze：捕获事实，不推进效果、不替换执行上下文
        -> 按原顺序递归处理 Commit 产生的子事件
        -> After.Prepare：原位置判断并准备、入队
    -> 调度器继续按原规则推进：事件队列优先
    -> On.Execute / After.Execute：轮到各自效果时结算
```

`On.Prepare`、`On.Execute`、`After.Prepare`、`After.Execute` 只是内部职责命名，不增加 DSL 时序字段。Commit 成功是对应 On 效果结算的必要条件，不表示立刻执行该效果。父子事件、After 条件判断、回合清理和死亡处理的相对位置均以现有调度为准。

失败路径保持当前停止规则：

```text
当前事件被 Before 阻止或 Commit 失败
    -> 不记录该事件的成功事实
    -> 不执行该失败事件尚未结算的普通 On 效果
    -> 按原规则停止、清理缓存或保留已完成部分的记录
```

已经执行的 Before 效果、已处理子事件和触发记录不被当成“尚未执行的普通 On 效果”；其保留或撤销规则按原实现逐项验收。

### 3.2 事件角色

服务端增加内部事件角色，不增加用户 DSL 字段：

```csharp
public enum GameEventRole
{
    ActionRequest,
    Fact,
    Internal,
    Projection
}
```

事件元数据至少需要表达：

```text
Role
CanTriggerCardAbility
VisibleInDsl
VisibleInGameLog
PersistPolicy
```

目标角色策略如下；阶段一先增加分类元数据，存量监听和历史收录范围完成差异确认后再启用限制：

| 角色 | 例子 | 普通卡牌能力 | 系统能力 | 默认进入历史 |
|---|---|---:|---:|---:|
| 请求 | `PlayCardRequested`、`AttackRequested` | 否 | 是 | 仅审计需要时 |
| 事实 | `PlayCard`、`Damage`、`Summon` | 是 | 是 | 是 |
| 内部 | `LeaveField`、`CardMoved`、状态刷新 | 否 | 按需 | 默认否 |
| 投影 | `HandUpdated`、广播或统计通知 | 否 | 否 | 否 |

## 4. DSL 兼容原则

保持现有配置形状：

```text
事件类型 + Before / On / After + 目标 + 区域 + 条件 + 效果
```

不新增以下用户字段：

```text
Role
CommitState
SnapshotPolicy
ParentEventId
TransactionId
```

编辑器显示名称调整为：

| 内部时序 | 用户显示 | 说明 |
|---|---|---|
| `Before` | 提交前 | 按原规则检查、拦截、改写并执行 Before 效果 |
| `On` | 发生时 | 在既有判定点确定资格，对应事件成功后按队列结算；普通可提交事件在提交前判定 |
| `After` | 提交后 | 当前事件提交及子事件处理后的既有 After 阶段；不表示所有 On 效果已结算 |

普通模式只显示成功事实事件；系统请求单独分组；内部事件和投影事件放入高级调试选项。

## 5. 分阶段实施计划

### 阶段一：固定事件语义和元数据

**目标：** 让服务端能够区分请求、事实、内部和投影事件。

**主要改动：**

- 在事件元数据或事件注册表中增加 `GameEventRole`。
- 给现有请求事件统一标记 `ActionRequest`。
- 给普通规则事件统一标记 `Fact`。
- 标记 `LeaveField`、`CardMoved`、状态刷新等内部事件。
- 标记只服务于前端或统计的投影事件。
- 先标记普通能力的目标事件权限，盘点存量请求、内部和投影事件配置；保存及运行限制在兼容差异确认后单独启用。
- 系统能力保留监听请求事件的能力。
- 增加服务端元数据查询，供前端分组使用。

**涉及入口：**

- `Server/Domain/Events/IGameEvent.cs`
- `Server/Domain/Events/EventType.cs`
- `Server/Domain/Events/Metadata/`
- `Server/Domain/Abilities/AbilityManager.cs`
- `Server/Controllers/AbilitiesController.cs`
- `src/components/TriggerConfigEditor.js`

**验收标准：**

- 元数据分类本身不改变存量普通能力的保存、匹配、执行和历史收录；启用权限限制前已有明确的存量处理方案及回归结果。
- 系统能力仍能监听请求事件。
- 普通 DSL 事件列表默认不出现内部和投影事件。
- 现有 DSL 配置无需增加新字段即可继续加载。

### 阶段二：区分 On 准备和结算，保持现有业务语义

**目标：** 显式区分触发资格与效果执行，不改变它们各自的判定时点、数据来源、取消规则及队列位置。用户仍只配置“事件类型 + On + 条件 + 效果”。

**实施顺序：**

1. 先为现有行为建立基线测试，补齐第 7 节的时点与顺序断言。
2. 先整理职责和命名，保留现有 `Effect` 队列、主能力预检缓存、延迟目标解析及参数求值路径。`On.Prepare` 与 `On.Execute` 可由现有模块的方法承担，不新增透传层或第二套调度器。
3. 冻结记录先接入捕获和投影，不替换 On/After 执行上下文；历史查询的读取切换另按阶段四验收。
4. 上述行为对照通过后，再单独迁移到稳定准备记录。避免同时替换缓存模型、条件求值、目标解析和调度顺序。

#### 2.1 触发资格按原判定点确定

- 普通可提交事件保留当前 Before 处理后的 On 匹配和条件检查位置。
- 部分主能力在更早的 `AnalyzePrimaryAbilitiesAsync` 中已判断的条件，继续沿用原缓存规则；暂停、恢复及取消后的清理行为保持一致。
- 原有触发器的事件、区域、沉默等筛选仍在原匹配点发生；预检缓存复用不等于跳过原本会再次执行的匹配步骤。
- 提交前已确定为真的能力级条件，不因提交后 PP、区域或定义变化而再次判断；已确定为假的条件也不在提交后补触发。
- 提交后只消费已准备的对应效果，不重新调用能力匹配入口为当前事件发现额外能力。派生事件继续独立运行自己的原有匹配流程。
- 完整保留旧表达式的求值上下文、短路和缓存语义；不按字段名称自动拆分表达式，也不引入将旧条件推迟到提交后判断的三态机制。
- 能力级条件与效果内分支、`RepeatCondition` 等不同；后两者按各自原时点计算，不一并冻结为提交前结果。

#### 2.2 目标与效果数值保留原求值时点

| 内容 | 兼容规则 |
|---|---|
| 已完成的玩家选择和决策 | 复用原选择结果，不重新询问、不重复随机抽取；保留取消和重试规则 |
| 原本提前解析的目标 | 保存已有结果及目标组信息，沿用原有效性检查 |
| `ResolveTargetsOnExecution` 对应目标 | 保存选择规则，到原结算位置解析，保留按能力与事件复用的解析缓存 |
| 已确定的费用、模式和常量 | 按原准备与提交校验规则保存；不覆盖旧效果中不同含义的动态表达式 |
| 效果参数公式 | 保留表达式及必要配置，仍在 `EffectExecutor` 的原求值位置计算 |
| 重复次数、重复条件、分支条件 | 保留各自原求值与缓存规则，包括已有决策预检结果的复用 |

锁定触发资格不等于锁定全部效果数值。示例：出牌前 PP 为 5，出牌后为 0，能力条件“PP >= 5”仍按原提交前结果触发；若某效果参数原本在结算时读取当前 PP，该参数继续读取结算时状态，而非强制固定为 5 或 Commit 瞬间的快照值。

#### 2.3 稳定准备记录的迁移约束

第一步继续使用现有运行时缓存；它与持久历史存储是不同用途。待行为对照通过后，引入 `PreparedAbilityPlan` 或等价内部记录，保存足够重建同一次效果请求的数据，而不是只保存一组固定数值。需要覆盖：

```text
触发身份：TriggerEventId、AbilityRuntimeId、AbilityDefinitionId、TriggerTiming
原求值结果：能力条件缓存、已完成的选择与决策、原本已确定的模式和费用
来源与失效规则：SourceCardInstanceId、原能力定义/必要配置快照、SourceAbilityStateVersion
目标：已解析的目标 ID 和目标组，或原延迟目标选择规则
参数：已求值常量，以及原本留待结算的表达式和配置
效果身份与顺序：原 EffectId、EffectIndex、执行顺序及队列位置
分支与重复：原 ExecutionIndex、SequenceScopePath 及决策缓存身份
诊断信息：原有状态版本和一致性校验信息，不新增一刀切失效规则
```

稳定记录仅保存必要的 ID、值、配置、表达式和选择结果，不复制完整 `GameState` 或持久保存可变实体引用。重新构造效果请求不重新匹配能力、不重新求触发条件、不额外消耗随机序列，也不改变事件/效果关联身份。来源能力已注销时，沿用原有定义快照和注销记录规则，避免仅凭运行时 ID 查找失败就丢弃效果。

一次触发准备结果至少按 `(TriggerEventId, AbilityRuntimeId, TriggerTiming)` 区分。同一事件可触发多个能力，禁止仅以 `EventId` 为去重粒度误删其他能力。一次准备结果只消费一次，且其多个效果、分支和合法重复仍按原索引与缓存身份执行。迁移前后以原有去重范围为基准，不新增限制。

#### 2.4 提交校验与排队效果取消分开处理

- 保留 `BuildCommitPlan`、`ValidateCommitPreflightConsistency` 及各事件 Commit 已有的费用、资源、目标和状态校验，保持校验范围与执行位置。
- 主事件被阻止或提交失败时，不执行其尚未结算的普通 On 效果；按原规则终止处理并清理相关缓存，不自动撤销此前已完成的状态变化。
- 已确定触发资格后，仍保留 `ShouldSkipQueuedEffectExecution` 的现有沉默、抑制、能力版本、注销记录和变身等取消规则；“不重判条件”不等于忽略这些规则。
- `StateRevision` 的正常推进不额外成为统一取消条件；只在旧实现原有校验位置使用原校验规则。
- 目标失效时按原流程决定跳过目标、跳过效果或报错；不统一升级为整个主行动失败，不额外增加重新准备、重新选择或重抽随机结果。

#### 2.5 保留队列及关联事件的完整顺序

- 保留能力注册/排序策略、同名触发名额、效果创建及入队顺序；不将 On 效果整体移至子事件或 After 效果之后再入队。
- Commit 成功后先沿原流程处理派生事件和 After 准备，再由现有调度器决定何时执行排队效果；不在 Commit 返回后同步执行全部 On。
- 保留事件队列优先、父子事件递归、延迟事件释放、回合清理、死亡处理和效果完成链的相对顺序。
- `RecordTrigger`、触发次数、`AbilityTriggered` 及其监听链保留原发生时点和失败路径记录；触发记录不被当作主事件提交成功的凭证。调整这些行为需独立提出差异并验证，不随命名整理一起实施。

#### 2.6 模式事件保留各自的判定边界

- 出牌模式、Enhance 费用和替代定义仍按原规则在出牌准备/校验中处理；已有模式主能力预检结果继续复用。
- `PlayCard.Commit` 成功后按原子事件顺序产生 `Enhance`、`Accelerate`、`Crystalize`。这些模式事件自身没有 Commit，普通监听条件保持在原事件处理点判断，即父级出牌已成功之后。
- 不把模式事件的所有监听条件提前到 `PlayCard.Commit` 前，也不将已有 `PlayCard.On` 条件后移到模式事件阶段。
- 既有 DSL 对当前 PP 的读取保持含义；模式事实的 `PaidCost` 等字段继续表达当次支付信息，二者不自动互换。
- 保留主能力替换、来源卡牌筛选和去重规则，避免重复执行同一主能力，同时保留其他合法的模式事件监听能力。

#### 2.7 执行视图与历史事实视图分别约束

- 触发资格使用原判定点的上下文和已有缓存。
- 效果执行时，原本读取当前战场、PP、目标或来源属性的表达式继续读取结算时状态；这可能晚于 Commit 成功瞬间。
- 冻结记录描述当次事件事实，服务历史、回放和投影；不将其整体替换为 On/After 的唯一上下文。执行中显式使用事件字段或历史查询的表达式，按字段映射与兼容测试逐项迁移。

**涉及入口：**

- `Server/Services/GameActionTransactionService.cs`
- `Server/Domain/Abilities/AbilityManager.cs`
- `Server/Domain/Abilities/IAbilityManager.cs`
- `Server/Domain/Abilities/Ability.cs`
- `Server/Domain/Abilities/Common/IAbility.cs`
- `Server/Domain/Abilities/Effects/EffectExecutor.cs`
- `Server/Domain/Abilities/System/`
- `Server/Domain/Events/ActionRequests/PlayCardRequestedEvent.cs`
- `Server/Domain/Events/PlayCardEvent.cs`

**验收标准：**

- 条件判定点、缓存复用、触发器匹配和触发结果与旧逻辑一致；提交后既不取消原本合法的资格，也不新增资格。
- 目标、参数、分支、重复和随机结果按原阶段与顺序求值；玩家选择次数一致。
- On、子事件、After、触发记录及清理事件的可观察顺序一致。
- 取消与失败处理符合旧规则，不因新的统一状态版本或目标检查扩大失败范围。
- 每个合法触发及效果执行次数一致，同一事件的多个能力和模式监听不被误去重。
- 第 7 节的针对性测试和行为差分通过后再切换稳定准备记录。

### 阶段三：建立统一冻结边界

**目标：** 为历史、回放和投影建立稳定事实视图，同时保留触发判定与效果执行各自的原数据来源。

**冻结规则：**

| 事件类型 | 冻结时机 |
|---|---|
| 请求事件 | 进入事务时捕获请求参数 |
| 可提交事实 | `Commit` 成功后立即捕获结果 |
| 非提交型事实 | 事件创建时捕获 |
| 派生事实 | 各自提交成功后捕获 |

非提交型派生事件按非提交型事实规则捕获，不补造 Commit。冻结过程只捕获数据，不提前执行效果，不改变触发次数、玩家选择或随机序列。`IntentPayload` 与 `FactPayload` 分别表达意图和提交结果，不互相覆盖；既有 DSL 事件字段的映射逐项验收。

**建议的内部记录：**

```text
FrozenEventRecord
- EventId
- EventType
- Role
- Timestamp
- TransactionId
- ParentEventId
- StateRevisionBefore
- StateRevisionAfter
- SourceId
- TargetIds
- IntentPayload
- FactPayload
- SourceSnapshot
- TargetSnapshots
- GeneratedEventIds
- SchemaVersion
```

**主要改动：**

- 新增集中式 `EventSnapshotFactory` 或同等职责的冻结服务。
- 优先使用已有 `CardInstanceSnapshot`、`CardDefinitionSnapshot` 和 `CardSnapshotCapture`。
- 完成历史读取迁移后，历史存储使用冻结数据；事务内 Commit、延迟目标解析和效果求值仍按既有规则读取运行时实体。
- 对冻结失败的事实，在开发和测试环境显式报错，不静默保存活引用。
- 不将提交后快照回填到已完成的 On 条件判定，也不将结算时的当前状态读取替换成 Commit 瞬间的快照。

**涉及入口：**

- `Server/Domain/Events/CardInstanceSnapshot.cs`
- `Server/Domain/Events/CardDefinitionSnapshot.cs`
- `Server/Domain/Events/CardSnapshotCapture.cs`
- `Server/Domain/Events/Services/`
- `Server/Services/GameActionTransactionService.cs`

**验收标准：**

- 历史、回放及前端事实投影使用同一份冻结记录；On/After 的判定和执行保留原上下文与求值时点。
- 执行中涉及事件字段或历史查询的表达式具有明确的新旧映射；行为差异按阶段四单独验收。
- 修改原始 `CardInstance` 后，已保存事件的快照不变化。
- 事件快照只包含 DSL 和回放需要的字段，不复制完整 `GameState`。

### 阶段四：改造历史和回放数据源

**目标：** 消除内存历史和 JSON 回放的双重语义。

**启用门槛：** 旧接口继续存在不等于旧 DSL 结果相同。切换前逐字段列出“旧读取来源、冻结字段、旧值、新值、受影响配置、是否允许变化”，覆盖当前实体引用、历史快照和显式实时查询的区别。历史漂移修复造成的差异单独确认；阶段二的 On 等价性测试不因此放宽。

**主要改动：**

当前 `IEventHistoryService` 直接解析到内存单例；持久回放仍由 `SqliteReplayJournal` 独立负责。本阶段的数据源统一尚未实施。

- `InMemoryEventHistoryService` 不再保存原始 `IGameEvent` 引用。
- 历史保存统一的冻结记录或冻结事件视图。
- 保留现有 `IEventHistoryService` 的兼容读取入口，内部改为读取冻结数据。
- 该内部读取切换仅在字段映射、存量配置差分与允许变化清单确认后启用；在此之前保留原读取行为，不将新记录强行接入全部执行上下文。
- 后续增加记录型读取接口，供 DSL 历史查询使用。
- `RawEventJson`、前端 DTO 和内存历史均从同一冻结记录生成。
- 保持 `EventId` 唯一，重复保存同一事件只更新同一条记录，不追加重复历史。
- 重复写入不重新从当前实体捕获并覆盖已冻结的事实载荷；需要补充的关联信息单独更新并保持原顺序。

**涉及入口：**

- `Server/Domain/Events/Services/IEventHistoryService.cs`
- `Server/Infrastructure/Services/InMemoryEventHistoryService.cs`
- `Server/Infrastructure/Services/JsonGameEventRawEventMapper.cs`
- `Server/Infrastructure/Services/SqliteReplayJournal.cs`
- `Server/Services/GameActionTransactionService.cs`

**验收标准：**

- 内存历史、回放 JSON、前端事件和 DSL 历史查询的 `EventId`、类型和快照一致。
- 变身、移动、属性变化不会修改旧事件。
- 现有回放读取不因新增字段而失败；未知字段可被旧读取器忽略。
- 旧 DSL 历史查询的行为差异有逐项确认记录，无隐式字段换义；原本显式读取当前状态的表达式继续保留实时含义。

## 6. 激奏、结晶、爆能专项规则

这三个事件保持为成功出牌后的模式事实，继续使用现有事件类型。其自身是非提交型事件，与父级 PlayCard 的提交前条件分别处理。

```text
PlayCardRequested
    -> 原有模式、费用校验和主能力预检
    -> PlayCard.Before
    -> PlayCard.On.Prepare 及原位置入队
    -> PlayCard.Commit 成功，返回既有次序的子事件集合
    -> 捕获 PlayCard 事实
    -> 按原子事件顺序处理 Accelerate / Crystalize / Enhance
       （其普通 On 条件在此判断，不提前到 PlayCard.Commit 前）
    -> 按原调度流程完成 After 准备并结算排队效果
```

实施要求：

1. 替代卡牌定义、费用和卡牌类型在变更状态前完成校验。
2. 替代形态和实际出牌必须属于同一个事务提交。
3. 如果出牌失败，不得留下已经变身的卡牌，也不得生成模式事实。
4. 模式事件保存模式、实际费用、替代定义 ID、卡牌实例 ID 和稳定快照。
5. 普通 DSL 默认监听 `Accelerate`、`Crystalize`、`Enhance` 的成功事实。
6. 既有模式主能力的选择和预检缓存仍按原流程复用；普通模式监听能力保留各自判定点，不统一合并成出牌前或出牌后重判。
7. 当前 PP、实际支付费用和模式事实分别保留含义，禁止自动改写旧 DSL 表达式或补触发原本未满足条件的能力。
8. 保留主能力替换及去重范围：同一主能力不重复结算，其他合法模式监听能力也不被删除。

第 2、3 项属于出牌原子性要求。若基线发现失败后残留变身等差异，应单独记录并修复该缺陷，不将改变失败副作用描述成 On 等价重构；是否允许变化按第 7.6 节确认。

## 8. 非目标和约束

本计划不包含：

- 重新设计全部事件名称。
- 把所有事件类一次性改成纯数据结构。
- 为每个事件保存完整 `GameState`。
- 让用户在 DSL 中配置事件角色或快照策略。
- 新增一套与现有 DSL 并行的规则语言。
- 立即删除所有内部事件。
- 在没有测试覆盖的情况下批量修改所有卡牌能力。
- 按条件读取字段自动决定提交前/后求值，或为旧能力增加提交后的再次匹配与补触发。
- 将所有目标和动态效果参数一律提前固定。
- 将 After 后移至全部 On 效果结算完成，或引入第二套效果调度器。
- 将冻结历史记录整体替换为所有能力的执行上下文。
- 扩大原有取消、状态版本或目标校验范围，或隐式改变失败后的部分提交行为。

采用兼容迁移：先补基线并增加不改变匹配行为的元数据；再在原调度路径上区分准备与执行职责；随后增加冻结捕获和投影；业务差分通过后单独迁移准备记录。历史读取切换和权限收紧须各自通过兼容门槛后启用，阶段编号不代表省略这些前置验收。
