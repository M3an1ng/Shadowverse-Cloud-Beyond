# 架构与代码导航

> 核对日期：2026-09-27。以目录和真实调用入口描述架构，不把旧设计中的抽象分层当作已存在的项目结构。

## 请求和对局链路

```text
index.html → src/main.js / router.js → 页面、编辑器、gameManager.js
  ├─ HTTP /api → Controllers → Services → ApplicationDbContext → SQLite
  └─ SignalR /gamehub → GameHub → GameService 动作队列
                         → GameActionTransactionService
                         → AbilityManager / 效果处理 / 领域事件
                         → 客户端事件映射、可玩性更新、回放相关组件
```

组装入口是 [Program.cs](../Server/Program.cs)。它负责注册依赖、配置 SQLite/日志、静态资源和中间件、映射两个 Hub 与控制器，并在启动时调用迁移和种子逻辑。

## 对局处理的实际边界

[GameService](../Server/Services/GameService.cs) 按单局 ID 维护动作队列，处理动作时创建服务作用域，生成初始事件并调用 `IGameActionTransactionService.ProcessTransactionAsync`。事务服务包含预检/提交阶段、目标与决策签名、待选目标和效果队列。修改动作流程时应阅读这一链路，不直接绕过它修改客户端数字。

游戏动作事务与 [TransactionService](../Server/Services/TransactionService.cs) 的数据库事务是不同职责。旧文档中“事务”一词可能混用，排查时先确认对应类型。

服务器负责规则结算；前端负责显示和发起动作。前端的可玩性提示、动画和本地缓存不应被当作最终规则裁决。领域事件、传输 DTO、日志快照也不是同一个对象。

## 保存与缓存

卡牌和能力修改涉及数据库、服务端目录和浏览器缓存。应同时检查控制器的 `X-Data-Revision`、`GameDataProvider` 以及前端数据变更通知，避免只刷新某个界面后误认为数据已一致。
