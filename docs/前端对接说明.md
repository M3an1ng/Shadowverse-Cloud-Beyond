# 前端对接说明

> 核对日期：2026-10-12。依据当前本地工作区的源码、配置及只读数据库统计编写，包含尚未提交的实现；不代表线上部署版本。
>
> 面向需要接入或重做前端界面的人。本文说明已经存在的协议，不要求前端重新实现战斗规则。

## 先看结论

| 你关心的内容 | 当前实现 |
|---|---|
| 使用什么语言 | 前端是原生 JavaScript、HTML、CSS，使用 Vite；后端是 C# / ASP.NET Core 8 |
| 怎么调用或连接 | 卡库、账号、牌组、房间走 HTTP JSON；对战走 `/gamehub` 的 SignalR |
| 局面怎么获取 | 接收 `ReceiveGameState` 全量状态，再处理具体事件；`TurnStarted` 也携带全量状态 |
| 玩家可以做什么 | 换牌、出牌、攻击、进化、超进化、PP+1、启动、融合、提交效果选择、结束回合、投降、聊天与表情 |
| 有多少卡牌 | 本地数据库有 **2,811 条卡牌定义**，其中 **2,234 条 `IsCollectible=true`**；仓库种子文件只有 **77 条**，不是完整卡库 |
| 阵营有多少 | 7 个职业 + 中立，共 8 类 |
| 有无 AI 对手 | **有**，由后端的规则型 AI 自动执行操作，不需要前端或大模型代打 |

两个必须区分的概念：

1. **HTTP 与 SignalR 的字段大小写不统一。** HTTP 普通属性通常是 camelCase；SignalR 普通属性保留 PascalCase；显式指定名称的字段仍使用指定名称。
2. **房间 ID 与单局 ID 不相同。** `roomId` 用于房间和连接，`activeGameId` / 局面中的 `GameId` 用于一局战斗。房间响应里的旧 `gameId` 实际兼容指向房间 ID。

### 2.2 HTTP 常用接口

请求 JSON 时使用 `Content-Type: application/json`；下面 `{roomId}` 是实际房间 ID，`{cardId}` 是整数卡牌定义 ID，`{deckId}` 是 GUID。

| 方法与路径 | 用途 | 请求 / 返回要点 |
|---|---|---|
| `POST /api/auth/register` | 注册 | 请求 `username`、`password`，可附带 `guestId` 迁移游客牌组 |
| `POST /api/auth/login` | 登录 | 请求 `username`、`password`；返回 `userId`、`username`、`avatarUrl`、`role`、`permissionLevel` 等 |
| `GET /api/cards` | 全部卡牌定义 | 直接返回数组，不是 `{items: [...]}`，也没有此端点的分页参数 |
| `GET /api/cards/{cardId}` | 单张卡牌定义 | 返回一个卡牌定义对象 |
| `GET /api/cards/{cardId}/abilities` | 一张卡的有效能力 | 返回能力数组，含关键词、描述与 `jsonConfig` |
| `GET /api/abilities/{abilityId}` | 单条有效能力 | 能力 ID 是数据库中的整数，不是本局运行时 GUID |
| `GET /api/decks?userId={userId}` | 账号牌组列表 | 返回牌组摘要数组 |
| `GET /api/decks?guestId={guestId}` | 游客牌组列表 | 游客身份与账号身份分开传递 |
| `GET /api/decks/{deckId}?userId={userId}` | 牌组详情 | 游客将查询参数换成 `guestId`；详情含 `cards` |
| `POST /api/match` | 创建房间 | 请求可含 `hostPlayerId`、`useAiFallback`、`ttlMinutes`；返回 201 和房间对象 |
| `GET /api/match` | 当前房间列表 | 返回 `{items: [...]}` |
| `GET /api/match/{roomId}` | 房间详情 | 返回房间对象 |
| `POST /api/match/{roomId}/join` | 加入房间 | 请求 `joinCode`，可含 `playerId`；响应提供客席信息 |
| `POST /api/match/{roomId}/deck` | 选择对战牌组 | 请求 `playerId`、`token`、`deckId`，再指定 `userId` 或 `guestId` |
| `POST /api/match/{roomId}/ready` | 准备 | 请求 `playerId`、`token` |
| `POST /api/match/{roomId}/start` | 房主开局 | 请求 `playerId`、`token`；需要已准备并选好合规牌组 |
| `POST /api/match/{roomId}/leave` | 离开房间 | 请求 `playerId`、`token`；不同于战斗中的投降 |
| `GET /api/emotes` | 表情目录 | 用目录中的表情 ID 发送表情 |
| `GET /api/tribes` | 种族目录 | 与职业 / 阵营不是同一概念 |
| `GET /api/localization/enums/{enumName}` | 枚举中文名称 | 返回标识到中文名称的字典；常用 `CardClass`、`CardType`、`CardKeyword`、`AbilityKeyword`、`PlayMode` |

牌组详情中的卡牌条目使用以下形式：

```json
{
  "cardDefinitionId": 1401302,
  "count": 3
}
```

这里的 `count` 是该定义在牌组中的张数，不是卡库条数；对战操作也不使用 `cardDefinitionId`，而是使用局面中的实例 GUID。

读取卡库的 JavaScript 示例：

```javascript
const response = await fetch('/api/cards');
if (!response.ok) {
  throw new Error(`读取卡库失败：${response.status} ${await response.text()}`);
}
const cards = await response.json();
console.log('当前 API 返回的卡牌定义数：', cards.length);
```

登录响应**没有账号 JWT / accessToken / refreshToken**。房间提供的 `hostToken` / `guestToken` 是对局席位连接令牌，不是账号登录令牌；`userId`、`guestId` 与席位 `playerId` 也不能自动视为同一个值。

### 2.3 房间到战斗的顺序

1. 登录或使用游客身份，读取该身份的牌组列表。
2. 房主创建房间，保存 `roomId`、`hostPlayerId`、`hostToken`、`joinCode`。
3. 真人对手使用邀请码加入，保存 `guestPlayerId`、`guestToken`；AI 模式的条件见第 8 节。
4. 玩家通过 `/deck` 选择自己的牌组。房间返回的 `requiredEnvironment` / `requiredRule` 用于约束对手选牌组。
5. 真人双方准备；房主调用 `/start`。房间状态依次涉及 `Waiting`、`Ready`、`Started`，关闭为 `Closed`。这些是字符串，不要假设 HTTP 的全部值都自动变成小写。
6. 开局响应中的 `activeGameId` 标识这一局；用 `roomId`、自己的席位 ID 和令牌建立 SignalR 连接。
7. 收到初始局面，完成换牌，然后按后端推送的当前玩家和可操作状态显示界面。

准备、选择牌组、开局等响应可能不返回令牌，**不能用响应中的 `null` 覆盖之前保存的席位令牌**。同一房间开始下一局时，应更新 `activeGameId`，清空上一局的界面状态。

房间接口常见错误：400 为参数 / 邀请码 / 牌组问题；403 为非参与者或无权操作；404 为不存在；409 为房间已满、已开始、已关闭、过期或开局条件不满足。错误响应可能是字符串，应先读取实际响应体，不要一律假设 `{message: ...}`。

源码依据：[房间控制器](../Server/Controllers/MatchController.cs)、[房间状态与开局条件](../Server/Services/MatchService.cs)、[牌组协议](../Server/Dtos/DeckDtos.cs)、[账号协议](../Server/Controllers/AuthController.cs)。

### 2.4 SignalR 连接示例

以下 `roomId`、`playerId`、`token` 来自上述房间流程；`renderGameState` 是接入前端自己的渲染函数，`showGameError` 是自己的错误展示函数。

```javascript
import * as signalR from '@microsoft/signalr';

const query = new URLSearchParams({ roomId, playerId, token });
const connection = new signalR.HubConnectionBuilder()
  .withUrl(`/gamehub?${query.toString()}`)
  .withAutomaticReconnect()
  .build();

// 必须先注册，再 start；服务器会在连接时发送初始状态。
connection.on('ReceiveGameState', state => renderGameState(state));
connection.on('TurnStarted', event => renderGameState(event.GameState));
connection.on('ReceiveError', message => showGameError(message));

// 实际界面还应注册第 4 节中用到的增量事件。
connection.onreconnected(async () => {
  await connection.invoke('RequestInitialGameState');
});

await connection.start();
```

- 新接入优先传 `roomId`；后端仍兼容 `gameId` 参数，当前旧前端连接代码也使用该兼容形式。
- 初始状态由服务器主动发送；需要重新同步时调用 `RequestInitialGameState()`。需要仅刷新可操作性时调用 `RequestPlayabilityUpdate()`。
- 现有玩家前端每 30 秒调用一次 `Heartbeat()`，用于刷新房间有效期；它是应用层心跳，不等于 SignalR 本身的连接检测。离开界面时停止该定时器和连接。
- 观战使用 `/gamehub?roomId=...&spectate=1`，房间必须已经开局。配置 `RequireJoinCodeForReplayReads=true` 时还需传 `joinCode`；可附带 `spectatorName`、`spectatorUserId`、`spectatorAvatar`。
- 观战不应显示战斗操作按钮；聊天走相应的观战身份上下文。

**`invoke()` 完成不代表战斗已结算成功。** Hub 多数战斗方法把动作放进队列；最终局面变化或失败要通过事件 / `ReceiveError` 确认。不要在 `invoke()` 成功后自行扣 PP、计算伤害或删除卡牌。

源码依据：[GameHub](../Server/Hubs/GameHub.cs)、[现有连接和事件注册](../src/main.js)、[现有动作调用](../src/gameManager.js)。

### 2.5 字段和枚举的大小写

| 数据通道 | 示例 | 原因 |
|---|---|---|
| HTTP 普通属性 | `roomId`、`playerId`、`cardDefinitionId` | HTTP 使用 camelCase |
| HTTP 真正的枚举属性 | 卡牌 `type: "follower"`、牌组 `class: "forestcraft"` | HTTP 枚举转换使用 camelCase |
| HTTP 已转成字符串的字段 | 卡牌定义 `class: "Forestcraft"`、`rarity: "Silver"`；房间 `status: "Started"` | 这些字段已经是字符串，不再套枚举大小写规则 |
| SignalR 普通属性 | `GameId`、`CurrentPlayerId`、`InstanceId`、`CurrentPP` | SignalR 保留 C# 属性名 |
| SignalR 枚举 | `Phase: "Main"`、`Type: "Follower"`、`Zone: "Hand"` | SignalR 枚举转换未设置 camelCase |
| 显式字段名 | 实例的 `id`、`counters`、`counterDisplayNames`、`counterSummaryEntries` | `[JsonPropertyName]` 覆盖命名策略，SignalR 中也保持这些名称 |

因此，**不能对全部响应机械地首字母转小写，也不能把静态卡牌定义直接当成对战实例**。字典键，例如可用性字典中的实例 GUID、本地化字典中的 `Forestcraft`，也是实际数据键。

## 3. 局面数据的结构

### 3.1 全量局面：`GameStateDto`

接收方法是 `ReceiveGameState(state)`。`TurnStarted(event)` 中的 `event.GameState` 是同一类结构。

| 字段 | JSON 类型 | 用途 |
|---|---|---|
| `GameId` | string | 本局 ID，不是房间 ID |
| `CurrentPlayerId` | GUID 字符串 | 当前行动玩家 |
| `FirstPlayerId` | GUID 字符串 | 先手玩家 |
| `Phase` | string | `Initialization`、`Mulligan`、`TurnStart`、`Main`、`Combat`、`TurnEnd`、`GameOver`；这是声明的阶段全集，不表示每局必经每个阶段 |
| `GameStatus` | string | `Starting`、`InProgress`、`Finished`、`Aborted` |
| `Players` | PlayerState 数组 | 两名玩家；按 `PlayerId` 找己方和敌方，不按数组位置判断视角 |
| `GameMessage` | string / null | 局面提示 |
| `TurnTimeoutSeconds` | number | 本局使用的回合时限 |
| `TurnStartedAtUtc`、`TurnEndsAtUtc` | UTC 日期字符串 / null | 回合起止时间，用于显示倒计时 |
| `IsGameOver` | boolean | 对局是否结束 |
| `WinnerId` | string / null | 获胜玩家 ID |
| `Player1`、`Player2` | PlayerState / null | DTO 的只读便捷属性也可能序列化；不要作为另一套状态源 |

**没有全局 `TurnNumber`。** 回合数位于每个玩家的 `TurnNumber`，当前回合数取 `CurrentPlayerId` 对应玩家的字段。

### 3.2 玩家状态：`PlayerStateDto`

| 类别 | 字段 | 说明 |
|---|---|---|
| 身份 | `PlayerId`、`IsAI`、`IsFirst`、`Class`、`DisplayName`、`AvatarUrl` | 识别玩家、先后手、职业与展示信息 |
| PP | `CurrentPP`、`MaxPP` | 当前与最大 PP |
| PP+1 | `PpBoostUsesAvailable`、`IsPpBoostArmed` | 剩余使用次数、是否已武装 |
| 进化 | `CurrentEP`、`MaxEP`、`IsEvolutionUnlocked`、`CanEvolve` | 当前点数、上限、解锁与本回合可用状态 |
| 超进化 | `CurrentSEP`、`MaxSEP`、`IsSuperEvolutionUnlocked`、`CanSuperEvolve` | 对应超进化状态 |
| 主战者 | `LeaderCard` | 卡牌实例；生命读取 `LeaderCard.CurrentHealth` 和 `LeaderCard.MaxHealth` |
| 牌库 | `DeckCount`、`Deck` | 牌库数量及实例数组；数量展示读取 `DeckCount` |
| 区域 | `Hand`、`Field`、`Graveyard`、`Extra`、`Emblem` | 手牌、战场、墓地、额外区、纹章区，均为实例数组 |
| 计数 | `GraveyardCount`、`BloodPool`、`PlayedCardCountThisTurn` | 墓场、血池与本回合用牌数量 |
| 自定义计数 | `counters`、`counterDisplayNames`、`counterSummaryEntries` | 值字典、显示名称字典、有序摘要条目；摘要条目为 `{key, label, value}` |
| 回合与换牌 | `TurnNumber`、`HasCompletedMulligan`、`HasTakenFirstTurn` | 玩家独立回合数、换牌完成状态；最后一项是保留的兼容字段 |

主战者不放在 `Field` 中，应独立渲染。`Emblem` 也不是普通战场格。

**信息展示边界：** 当前初始状态路径直接映射完整局面，DTO 与映射包含 `Hand` 和 `Deck`，没有在这条路径按对手视角过滤手牌 / 牌库。不要根据“理论上看不到”就假设响应一定只有数量。界面应按玩法区分公开区域、己方手牌、对手牌背和观战视角；本文不把当前协议描述成已实现服务器端隐藏信息裁剪。

### 3.3 对战卡牌实例：`CardInstanceDto`

| 类别 | 字段 | 说明 |
|---|---|---|
| 两种 ID | `InstanceId`、`id` | `InstanceId` 是本局实例 GUID；`id` 是静态定义整数 ID。同名的两张牌也有不同实例 GUID |
| 基本资料 | `Name`、`CardNames`、`Type`、`Rarity`、`Class`、`Tribe`、`Description` | `CardNames` 是可被视为的名称列表；`Tribe` 是种族字符串数组 |
| 费用 | `Cost`、`CurrentCost` | 原始费用与当前费用；打出模式费用还需看可用性更新 |
| 属性 | `Attack`、`Health`、`CurrentAttack`、`CurrentHealth`、`MaxAttack`、`MaxHealth` | 基础属性与当前 / 最大属性；`MaxAttack` 可为 null |
| 位置与归属 | `Zone`、`ZoneIndex`、`OwnerPlayerId`、`ZoneStayTurn` | 区域、区域位置、拥有者、在当前区域停留的回合数；`ZoneIndex` 可为 null |
| 攻击 | `CanAttack`、`AttacksThisTurn`、`MaxAttacksPerTurn` | 可攻击状态、已用次数、上限 |
| 进化 | `CanEvolve`、`IsEvolved`、`IsSuperEvolved`、`EvolvedState` | 实例固有进化资格与当前状态；`EvolvedState` 可为 null |
| 启动 | `ActAbilities`、`ActsThisTurn`、`MaxActsPerTurn` | 能力摘要、已用次数、上限 |
| 融合 | `FusionAbilities`、`FusedCards`、`FusionsThisTurn`、`MaxFusionsPerTurn` | 能力摘要、融合材料实例、已用次数、上限 |
| 关键词与描述 | `Keywords`、`EffectDescriptions` | 实例关键词字符串数组，效果展示文本数组；后端执行实际规则 |
| 护符与土之印 | `CurrentCountdown`、`Earthsigil` | 当前倒数可为 null；注意 `Earthsigil` 的实际拼写 |
| 计数与增益 | `counters`、`counterDisplayNames`、`counterSummaryEntries`、`BuffSummaries`、`BuffStatSummary` | 计数与增益摘要，供详情展示 |
| 图片 | `ArtPreview`、`ArtDetail` | 预览和详情图片路径，可为 null |

`ActAbilities` / `FusionAbilities` 的每项为 `{RuntimeId, Name, Description}`。发送启动 / 融合时的 `AbilityRuntimeId` 要来自这里或服务器可用性数据，不能替换成数据库能力整数 ID。

区域枚举：`Field`、`Hand`、`Deck`、`Graveyard`、`Extra`、`Emblem`、`Playing`、`Removed`、`Staging`、`None`。后四项包含结算中的临时 / 非常驻区域，不必各自创建一个常驻 UI 面板。

源码依据：[局面 DTO](../Server/Dtos/GameStateDto.cs)、[玩家 DTO](../Server/Dtos/PlayerStateDto.cs)、[实例 DTO](../Server/Dtos/CardInstanceDto.cs)、[玩家映射](../Server/Mappings/PlayerStateProfile.cs)。

## 4. 事件有哪些种类

### 4.1 三层名称不要混用

1. **前端订阅名**：例如 `connection.on('CardPlayed', handler)`。
2. **事件 DTO 的 `Type`**：事件内容中的标识，不要求与订阅名或领域枚举同名。
3. **后端领域事件 `EventType`**：用于能力触发、结算和记录，例如 `PlayCard`、`Damage`、`Destroy`。不是所有领域事件都有一个同名 SignalR 订阅。

接入 UI 以下面的**订阅名**为准。多数游戏事件继承 `GameEventDto`，带有 `Type`、`SourcePlayerId`、`TimestampUtc`、可为 null 的 `Announcement`；全量局面、聊天、可用性等对象不应强行套用这一层结构。`SourcePlayerId` 也不总等于受伤目标或被更新卡牌的拥有者，应读取事件专用的目标字段。

### 4.2 当前客户端接口的订阅名

| 分类 | 订阅名 | 前端处理重点 |
|---|---|---|
| 全量同步 | `ReceiveGameState` | 使用局面快照同步界面 |
| 回合 | `TurnStarted`、`TurnEnded`、`PlayerMulliganCompleted` | `TurnStarted.GameState` 是新快照；换牌与行动方展示 |
| 连接 | `PlayerConnectionStatusUpdated` | `PlayerId`、`IsConnected`、`Reason` |
| PP | `PpUpdate`、`PpMaxUpdate`、`PpBoostStateUpdated` | PP 事件字段是 `CurrentPp` / `MaxPp`，不同于玩家状态中的 `CurrentPP` / `MaxPP`；PP+1 更新有 `IsArmed` |
| 进化资源 | `EpUpdate`、`EpMaxUpdate`、`SepUpdate`、`SepMaxUpdate` | 读取对应 `CurrentEp` / `MaxEp`、`CurrentSep` / `MaxSep` |
| 行动状态 | `AttackStateUpdated`、`EvolveStateUpdated`、`SuperEvolveStateUpdated`、`ActStateUpdated`、`FusionStateUpdated` | 更新实例或玩家按钮；攻击、启动、融合使用 `TargetCardInstanceId` |
| 手牌与牌库 | `HandUpdated`、`DeckUpdate` | `UpdatedHand` 是手牌数组；`DeckCount` 是最新牌库数量 |
| 墓地与纹章 | `GraveyardUpdate`、`EmblemUpdated` | 更新墓场计数 / 条目和 `AddedEmblems` |
| 实例同步 | `CardInstanceUpdated`、`CardMoved`、`CounterChanged` | 批量 `UpdatedCards`；移动的 `CardUid`、`FromZone`、`ToZone`；计数器新旧值 |
| 出牌与召唤 | `CardPlayed`、`CardSummoned` | 实例分别位于 `PlayedCardInstance`、`SummonedCard`，不能混用字段名 |
| 进化结果 | `UnitEvolved` | 使用 `EvolvedUnitState` 更新实例；实例上的 `IsSuperEvolved` 区分超进化结果 |
| 离场 | `UnitDestroyed`、`CardVanished`、`CardReturned`、`Tuck` | 破坏、消失、回手、洗入牌库；按事件目标 ID 与区域更新同步，避免重复移除 |
| 攻击与伤害 | `AttackDeclared`、`DamageDealt`、`HealApplied`、`HealthChanged`、`StatChange` | 动画与数值同步分开；伤害量不是最新生命值 |
| 关键词 | `KeywordAdded`、`KeywordRemoved` | 读取 `CardInstanceId` 和 `Keyword` |
| 能力展示 | `AbilityTriggered`、`Fusion`、`CardRevealed` | 能力提示、融合动画、公开卡牌；`Fusion` 是结果事件，操作入口叫 `RequestFusion` |
| 手牌可用性 | `ReceiveHandPlayabilityUpdate` | `PlayerId` + `PlayabilityResults` 字典 |
| 启动可用性 | `ReceiveActPlayabilityUpdate` | 场上启动按钮及分能力费用 / 目标 |
| 单项可用性接口声明 | `ReceivePlayabilityResult` | 接口保留此名称；当前主要接入应使用上面的批量更新，不假设每次出牌都会收到单项结果 |
| 等待玩家选择 | `PlayerChoiceRequested` | 读取 `ChoiceRequest`，显示候选和选择数量限制 |
| 结束 | `GameOver` | `WinnerId`、`LoserId`、`Reason`；停止显示战斗操作 |
| 错误 | `ReceiveError` | 参数直接是错误字符串，不是事件 DTO |
| 战斗记录 | `MatchHistorySync`、`LogEvent` | 已使用 / 已破坏卡牌记录、领域事件日志展示 |
| 聊天 | `ChatHistory`、`ChatMessage` | 历史和新消息；`MessageType` 区分文本 / 表情 / 系统消息 |
| 开发诊断 | `ConditionTraceFailed`、`ConditionTraceSucceeded` | 开发控制台能力条件跟踪，不作为战斗数值来源 |
| 通用事件 | `ReceiveGameEvent` | 专门映射之外的事件；按 `Type` 和实际字段识别 |

这张表列出客户端接口的完整方法名；**接口有声明不代表每次操作都会产生该事件**。卡牌能力、阶段、收件人和映射决定具体推送。

`BuffAppliedEventDto`、`BuffRemovedEventDto`、`SilenceAppliedEventDto`、`SilenceRemovedEventDto`、`CardDrawnEventDto`、`CardDiscardedEventDto` 等 DTO 文件虽然存在，但当前映射没有为它们分别声明同名客户端方法；不能仅按文件名注册订阅。未专门映射的 DTO 走 `ReceiveGameEvent`，界面上的手牌、属性与增益还要结合对应同步事件和实例摘要。

### 4.3 处理事件时避免重复计算

- `DamageDealt` 适合展示伤害数字；`HealthChanged.NewHealth` 是最新生命值。不要又减一次 `DamageAmount`。
- `CardInstanceUpdated.UpdatedCards` 是实例快照。按 `InstanceId` 更新，不能按静态 `id` 替换所有同名卡。
- `HandUpdated.UpdatedHand` 是完整手牌更新，不是在旧数组末尾附加一次。
- `CardMoved`、出牌、召唤、离场事件可能描述同一条结算链；同一实例应按区域保持唯一，不重复插入。
- 连接中断或状态不一致时，可以调用 `RequestInitialGameState()` 恢复；收到全量快照后不要再次手工套用同一操作的预估结果。

## 5. 玩家能做哪些操作

### 5.1 战斗方法与准确参数

以下为 `connection.invoke(方法名, 参数)`，动作对象沿用当前前端的 PascalCase。GUID 在 JavaScript 中都是字符串。

| 玩家操作 | Hub 方法 | 参数 |
|---|---|---|
| 起手换牌 | `SubmitMulligan` | 直接传待替换实例 GUID 的字符串数组；不换牌也提交 `[]` |
| 出牌 | `PlayCard` | `{CardUid, TargetUids?, PlayMode?, AbilityRuntimeId?, PaidCost?}` |
| 从者攻击 | `PerformAttack` | `{AttackerUid, TargetUid}` |
| 进化 | `PerformEvolve` | `{UnitUid}` |
| 超进化 | `PerformSuperEvolve` | `{UnitUid}` |
| 后手 PP+1 | `PerformPpBoost` | 不传参数 |
| 启动能力 | `RequestAct` | `{CardUid, AbilityRuntimeId?}` |
| 融合 | `RequestFusion` | `{CardUid, AbilityRuntimeId?}`；材料选择通过后续选择事件完成 |
| 提交效果选择 | `SubmitTargetChoice` | `{PendingChoiceId, SourceAbilityRuntimeId, TargetKey, ChosenTargetIds, WasCancelled}` |
| 结束回合 | `EndTurn` | 直接传请求 ID 字符串，不是 DTO 对象 |
| 投降 | `Surrender` | 直接传请求 ID 字符串 |
| 文本聊天 | `SendChatMessage` | `{ClientMessageId?, Content, MessageType: "text"}` |
| 表情 | `SendChatMessage` | `{ClientMessageId?, MessageType: "emote", EmoteId}`；ID 取自表情目录 |
| 重新同步局面 | `RequestInitialGameState` | 不传参数 |
| 刷新可用性 | `RequestPlayabilityUpdate` | 不传参数 |
| 房间心跳 | `Heartbeat` | 不传参数 |

开发入口另有 `ExecuteDebugCommand({Command, Args})`，不属于普通玩家战斗操作。`CatchUp(fromSeq, limit)`、`Seek(targetSeq)` 用于已记录事件的补流 / 跳转；默认配置 `Replay.EnableJournalWrites=false`，不能把它们当成默认就有完整回放的保证。

典型调用形式，变量均取自当前服务器状态或待提交选择：

```javascript
await connection.invoke('PlayCard', {
  CardUid: card.InstanceId,
  TargetUids: []
});

await connection.invoke('PerformAttack', {
  AttackerUid: attacker.InstanceId,
  TargetUid: opponent.LeaderCard.InstanceId
});

await connection.invoke('PerformEvolve', { UnitUid: follower.InstanceId });
await connection.invoke('EndTurn', crypto.randomUUID());
```

攻击主战者时传 **`opponent.LeaderCard.InstanceId`**，不是对手 `PlayerId`。`EndTurnActionDto` 文件存在也不改变 Hub 当前接收字符串的事实。

### 5.2 出牌模式与按钮可用性

`PlayMode` 有四种：`Base`（基础）、`Enhance`（爆能）、`Accelerate`（激奏）、`Crystalize`（结晶）。**协议实际拼写是 `Crystalize`，不是 `Crystallize`。**

`ReceiveHandPlayabilityUpdate` 的结构：

- `PlayerId`：本次更新针对的玩家。
- `PlayabilityResults`：键是手牌实例 GUID，值是 `PlayabilityResultDto`。
- 结果字段：`IsPlayable`、`RequiresTargetSelection`、`HasValidTargets`、`FailureReason`、`ValidTargetIds`、`CanPlayWithoutTarget`。
- 模式字段：`PlayModes`、`SelectedPlayMode`、`SelectedAbilityRuntimeId`；每个模式包含 `Mode`、`EffectiveCost`、`IsAvailable`、`Reason`。

前端用这些数据决定是否亮牌、显示模式菜单、展示费用和高亮目标。选择非基础模式时，按所选模式发送 `PlayMode`、`PaidCost` 和对应运行时能力 ID；`PaidCost` 是前端预期费用，实际支付仍由后端校验。不能只比较 `CurrentPP >= card.Cost`。

`ReceiveActPlayabilityUpdate` 也以实例 GUID 为字典键；结果有 `ActCost`、`IsPlayable`、目标信息及 `Abilities` 数组。多启动能力时应按具体 `AbilityRuntimeId` 显示可用性，不能只给整张卡一个统一按钮状态。

进化按钮要同时看玩家的解锁 / 点数 / `CanEvolve` 和实例资格；超进化、攻击、PP+1、启动、融合也不能仅根据外观或类型推断可用。

### 5.3 服务端要求玩家选择时

接收 `PlayerChoiceRequested(event)`，读取 `event.ChoiceRequest`：

| 字段 | 说明 |
|---|---|
| `PendingChoiceId` | 这次待完成选择的 ID |
| `GameId`、`RequestingPlayerId` | 所属对局和需要选择的玩家 |
| `SourceAbilityRuntimeId`、`TargetKey` | 原样带回的能力运行时 ID 和选择键 |
| `Message` | 选择提示 |
| `SelectableTargetIds` | 可选目标实例 GUID |
| `SelectableCardInstances` | 可渲染的候选实例，适用于牌库、墓地等当前不在可点击区域的候选 |
| `MinSelectionCount`、`MaxSelectionCount` | 最少 / 最多选择数 |
| `IsCancellable` | 是否允许取消 |

提交示例：

```javascript
await connection.invoke('SubmitTargetChoice', {
  PendingChoiceId: choice.PendingChoiceId,
  SourceAbilityRuntimeId: choice.SourceAbilityRuntimeId,
  TargetKey: choice.TargetKey,
  ChosenTargetIds: selectedIds,
  WasCancelled: false
});
```

只有 `IsCancellable=true` 时才提供取消操作，并按协议提交 `WasCancelled: true`。不同效果不一定都是“点一个场上单位”；需要支持多选、候选卡面板和无须选目标的情况。

源码依据：[动作 DTO 目录](../Server/Dtos/SignalR/Actions/)、[可用性 DTO](../Server/Dtos/PlayabilityResultDto.cs)、[模式可用性](../Server/Dtos/PlayModeAvailabilityDto.cs)、[选择请求](../Server/Domain/Abilities/Targets/PlayerChoiceRequest.cs)。

## 6. 卡牌资料的格式和数量

### 6.1 静态定义格式

`GET /api/cards` 返回 `CardDefinitionDto[]`。下面是本地卡牌“商队猛犸象”的**主要字段示例**，按源码序列化规则呈现，不是本次抓取的 HTTP 响应；完整字段见表格。

```json
{
  "id": 1401302,
  "name": "商队猛犸象",
  "type": "follower",
  "rarity": "Silver",
  "card_set": "星云基础",
  "card_set_definition_id": 2,
  "class": "Neutral",
  "cost": 7,
  "attack": 10,
  "health": 10,
  "countdown": null,
  "description": "",
  "artPreview": "/assets/cards/1401302/preview.webp",
  "artDetail": "/assets/cards/1401302/detail.webp",
  "isCollectible": true,
  "keywords": [],
  "tribe": []
}
```

| 字段 | 类型 / 用途 |
|---|---|
| `id` | number，卡牌定义 ID |
| `name` | string，卡名 |
| `type` | HTTP 枚举字符串：`leader`、`follower`、`spell`、`amulet`、`crest`、`faith` |
| `rarity` | string，通常来自 `CardRarity.ToString()`：`Special`、`Bronze`、`Silver`、`Gold`、`Legend` |
| `class` | string，职业标识，见第 7 节 |
| `cost` | number，基础费用 |
| `attack`、`health`、`countdown` | number / null，不同卡牌类型不一定使用这些字段 |
| `description` | string / null，展示文本，不是可执行效果代码 |
| `card_set` | string，卡包 / 系列名称 |
| `card_set_definition_id` | number / null，卡包定义 ID |
| `card_set_code`、`card_set_abbr` | string / null，卡包代码与简称 |
| `card_set_environment` | 枚举字符串数组 / null，可用环境，例如 `rotation`、`unlimited`、`open`、`compile` |
| `artPreview`、`artDetail` | string / null，预览图与详情图路径；不要使用旧种子中的 `art` 字段代替 API 协议 |
| `updatedAt`、`updatedBy` | 日期字符串 / null、string / null，编辑信息 |
| `isCollectible` | boolean，可收藏定义标识；不等于当前账号已经拥有、也不等于所有环境都可入牌组 |
| `keywords` | string 数组，卡牌状态关键词 |
| `tribe` | string 数组 / null，种族 |
| `effects` | 简单效果数组 / null，条目为 `{trigger, action, value, target}`；这是保留的简化格式，不是完整能力 DSL |

实际能力另从 `/api/cards/{cardId}/abilities` 取得，常见字段有 `id`、`name`、`description`、`abilityKeywords`、`abilityType`、`priority`、`isActive`、`cardId`、`jsonConfig`。关键词条目包含 `keyword` / `value` 信息；`jsonConfig` 描述触发、条件、目标、效果等能力配置，正常有效数据是解析后的 JSON 对象，不能一律对其再执行 `JSON.parse()`。卡牌能力接口在配置解析异常时也可能返回原字符串，应根据实际类型处理。

只做游戏界面时，前端主要展示卡牌定义、实例和能力文本，**不应在浏览器执行 DSL 来决定战斗结果**。如要接入卡牌 / 能力编辑器，再参考 [卡牌创作与 DSL](05-卡牌创作与DSL.md)。

## 8. 有没有 AI 对手

**有，当前已实现后端规则型 AI。** `PlayerStateDto.IsAI` 用于识别 AI 玩家。它不依赖前端生成动作，也不是调用大模型 API 的聊天式 AI。

### 8.1 怎么创建 AI 对战

1. `POST /api/match` 创建房间时设置 `useAiFallback: true`。
2. 房主调用 `/api/match/{roomId}/deck` 选择自己的 `deckId`，同时传 `aiDeckId` 或 `aiDeckCode` 选择 AI 牌组。
3. 若 AI 牌组属于另一身份，可传 `aiUserId` 或 `aiGuestId`；未提供 AI 所有者时，当前后端按房主牌组所有者查询。
4. 房主准备并开局，使用自己的席位信息连接 `/gamehub`。

当前 AI 补位条件是 **`useAiFallback=true` 且没有真人客席**；真人客席存在时按真人双方准备条件处理。这不是断线后自动把真人替换成 AI 的承诺。AI 牌组必须已选择完成，并与玩家牌组匹配环境 / 规则；不能只设一个 `useAiFallback` 就假设后端随意生成牌组。

### 8.2 AI 当前会做什么

- 起手换牌：按规则选择高费用牌，当前策略会换掉费用大于 3 的牌。
- 回合执行：检查 PP+1，然后尝试出牌、进化、逐次攻击；没有更多动作时结束回合。
- 策略是代码中的简化规则和优先级，不是复杂搜索或模型推理。
- 前端和真人战斗一样接收局面与事件，无需单独实现 AI 事件协议。

**能力边界：** 当前执行器没有独立的超进化、启动、融合决策步骤；不要把“玩家接口存在”解释成“AI 会使用全部玩家操作”。本文只核对实现，没有运行一整局来保证任意牌组和复杂能力组合都能被 AI 正确使用。

源码依据：[AI 决策](../Server/Services/AiService.cs)、[AI 回合执行](../Server/Services/AiTurnExecutor.cs)、[AI 房间条件](../Server/Services/MatchService.cs)。

## 9. 对接时最后核对的事项

- 静态卡牌定义 ID、对战实例 GUID、数据库能力整数 ID、能力运行时 GUID 各自分开。
- 房间 HTTP 流程先完成，再进入战斗；使用自己的席位令牌，不用登录响应推导。
- 事件在连接前注册；初始同步、增量事件和重连同步都能处理。
- 以服务端可用性和结算事件驱动 UI，不自行支付费用、计算伤害或执行卡牌 DSL。
- 选择界面支持数量限制、取消权限和当前场外候选卡牌。
- 所有数量都注明环境口径；部署后按 API 重新读取卡库，不把种子数量当完整数量。
