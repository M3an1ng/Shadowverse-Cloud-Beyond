# 文档维护规则

> 本文确立维护约定，不描述尚未实现的游戏功能。生效日期：2026-09-27。

## 单一入口，不重复写同一事实

- 根 [README](../README.md) 只做简介与入口；[docs/README](README.md) 按任务导航。
- 当前实现写入 01—07 对应主题；保留核对日期与源码/测试链接。
- 未来需求写进 OpenSpec 或专项设计，明确“规划”“待实现”“待验证”。
- 历史设计和过期进度进入带日期的归档，旧路径只留兼容跳转。
- 根目录 Memory Bank 已转为入口，不再复制当前任务状态或维护第二份项目进度。

## 什么变更需要更新哪里

| 代码变化 | 文档 |
|---|---|
| 新页面或用户功能 | 项目现状；涉及规划变化再更新对应需求 |
| 依赖、启动端口、测试命令 | 开发与验证 |
| 模块职责或调用路径变化 | 架构与代码导航 |
| 回合、牌组、任务、房间生命周期变化 | 对战与玩法 |
| 能力字段、解析与编辑器读写变化 | 卡牌创作与 DSL |
| API、DTO、身份或数据库变化 | 接口与数据 |
| 配置、发布、日志或故障处理变化 | 运行部署与排障 |

版本号从项目/锁文件核对；字段从 DTO/模型核对；规则从实现与测试核对。少复制代码块、枚举全集和伪精确的完成百分比。描述“文件已存在”“实现已核对”“测试通过”“已部署”时分别提供相应证据。

## 归档流程

1. 先核对内容和调用/引用关系；混合规划与事实的说明不直接当成现行规范。
2. 原文按原相对路径保存到日期归档，保留字节和哈希；新增说明放归档索引，不修改历史原文。归档目录的 `.gitattributes` 关闭 Markdown 换行转换，保证后续 Git 签出仍可核验原字节。
3. 在迁移清单记录原路径、历史路径、原因和当前入口。
4. 旧路径保留简短跳转，确保源码注释、技能说明、旧提案能找到历史或当前文档；归档说明使用 `INDEX.md`，避免覆盖原根 README。
5. 运行文档校验，再核对改动范围。涉及批量移动、删除仍遵循 [AGENTS.md](../AGENTS.md) 的确认规则。

本次清单：[归档清单](归档清单.md)。兼容跳转不代表仍维护旧架构；查找代码时优先阅读新文档。

## OpenSpec 的特殊处理

OpenSpec 变更归档会影响主规范，和普通文档搬家不同。任务全勾选只说明任务文件的状态，不证明实现、测试和主规范已同步。

对指定变更依次核验：提案/设计 → 任务 → 增量规范 → 当前代码 → 对应场景测试 → 与主规范及其他变更的冲突。按项目对应 OpenSpec 技能执行同步和归档；未完成证据核对的变更保留原位置。

本次生成 [OpenSpec 待核实清单](OpenSpec待核实清单.md)，不批量改勾选、不把多个时代的增量规范按文件日期直接合并。尤其关注未完成验证项、只有 proposal 的变更和跨变更的替代关系。

## 完成检查

```powershell
python "scripts/check-docs.py"
```

检查当前维护文档和兼容入口中的本地链接、Markdown 锚点、UTF-8 可读性，以及归档原文 SHA-256。历史原文、已有研究与专项计划不在链接强制检查范围内，避免为了消除历史问题破坏原文。

每次维护记录实际执行过的验证；没有执行的浏览器、对局、迁移或部署验证单独列出。事实出现冲突时修订当前文档，不通过修改业务代码去迎合旧说明。
